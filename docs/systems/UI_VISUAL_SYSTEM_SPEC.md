# Nastya Story — UI Design System

Статус: **утвержденная базовая дизайн-система v1**.

Этот файл — **единственный основной источник визуальных правил игрового интерфейса Nastya Story**. Реализация в Ren'Py, графические ассеты и будущие TASK должны следовать этому документу и не вводить параллельные визуальные правила без отдельного утверждения владельца.

## 1. Роль документа и рабочий процесс

UI проектируется и проверяется непосредственно для итоговой среды игры — Ren'Py на целевом разрешении и поверх реальных игровых фонов.

Основной процесс:

`UI Design System → при необходимости референс/ассет → Ren'Py → проверка в игре → корректировка Design System при утвержденном изменении`

### 1.1. Figma

Figma **исключена из обязательного производственного процесса** проекта.

- Figma не является источником канона или визуальных токенов.
- Наличие макета в Figma не требуется перед реализацией интерфейса.
- Платные функции, токены, Code Connect и библиотеки Figma не являются зависимостью проекта.
- Figma может использоваться эпизодически как необязательный инструмент для чернового макета сложного экрана, если это действительно экономит время.
- При конфликте макета Figma с этим документом приоритет имеет этот документ.
- Вся информация, необходимая Codex для реализации интерфейса, должна находиться в GitHub, а не только во внешнем дизайнерском сервисе.

### 1.2. Approved visual references

Для четырех ключевых экранов утверждены исходные визуальные референсы:

- [телефон](../../assets/ui/approved_references/phone.png);
- [карточка Насти](../../assets/ui/approved_references/nastya-card.png);
- [гардероб](../../assets/ui/approved_references/wardrobe.png);
- [инвентарь](../../assets/ui/approved_references/inventory.png).

Пояснение к статусу и области действия референсов: [`../../assets/ui/approved_references/README.md`](../../assets/ui/approved_references/README.md).

Эти изображения являются **approved visual references** для:

- общей композиции экранов;
- предметной оболочки;
- визуальной иерархии;
- характера панелей, сеток и карточек;
- общего направления оформления.

Они **не являются**:

- источником игровых фактов, биографии, расписаний, баланса или механик;
- pixel-perfect макетами, которые требуется копировать координата-в-координату;
- источником точных цветов, размеров, шрифтов, радиусов и состояний компонентов, если правило уже задано настоящей дизайн-системой;
- основанием сохранять устаревшие подписи или данные, видимые на старом макете.

При конфликте между approved visual reference и настоящим документом приоритет имеет настоящий документ. При конфликте текста на референсе с каноническими системными/world/content-файлами приоритет имеют соответствующие канонические источники.

Approved visual references не должны использоваться как готовые runtime-скриншоты с запеченным текстом и устаревшими данными. Реализация должна воспроизводить их композиционный и предметный принцип средствами компонентов и отдельных ассетов.

## 2. Общий визуальный язык

Интерфейс должен ощущаться частью взрослой современной визуальной новеллы, а не отдельным мобильным или веб-приложением поверх изображения.

Основные принципы:

- полноэкранное изображение локации остается главным визуальным слоем;
- центральная область кадра максимально свободна для персонажей и сцены;
- HUD компактный, предметный и визуально легкий;
- крупные интерфейсные системы имеют узнаваемую предметную оболочку;
- декоративность не мешает функциональности;
- цвет используется для семантики, а не для случайного украшения;
- все повторяющиеся элементы принадлежат одной системе размеров, отступов, состояний и типографики;
- случайные эмодзи, Unicode-символы вместо штатных пиктограмм и несогласованные наборы иконок в финальном UI запрещены.

### 2.1. Предметность крупных экранов

- телефон — современный смартфон;
- инвентарь — раскрытая цветная коробка с функциональной сеткой внутри;
- гардероб — открытый шкаф, слева зеркало с персонажем, справа сетка одежды;
- доступ к единому гардеробу на работе — шкафчик/секция раздевалки на той же компонентной основе; отдельная коллекция вещей не создается;
- содержимое таких экранов строится обычными сетками, списками и кнопками: декоративный фон не определяет игровую логику расположения элементов.

## 3. Базовая координатная система

Целевой базовый макет интерфейса: **1920×1080**.

Все размеры ниже относятся к этому базовому разрешению. При масштабировании Ren'Py сохраняются относительные пропорции и читаемость.

### 3.1. Центральная безопасная область

Рекомендуемая свободная область HUD:

- `x = 300…1620`;
- `y = 145…875`.

Постоянные крупные непрозрачные панели внутри этой зоны запрещены. Временное контекстное окно может кратковременно заходить в безопасную область.

### 3.2. Сетка отступов

Базовый модуль: **4 px**.

Основные допустимые значения:

`4 / 8 / 12 / 16 / 24 / 32 / 48 px`

Для новых компонентов сначала используются эти значения. Произвольные отступы допустимы только при явной композиционной необходимости.

### 3.3. Радиусы

- малый элемент/бейдж: `8 px`;
- обычная кнопка/карточка: `12 px`;
- крупная панель: `16 px`;
- модальная оболочка: `20 px`;
- медальоны HUD: круг `50%`.

Не смешивать большое количество разных радиусов на одном экране.

## 4. Цветовая система

В UI-коде нельзя вводить произвольные цвета непосредственно внутри screen-блоков, если для них существует семантический токен. Все повторяемые цвета должны определяться централизованно в дизайн-системе реализации.

### 4.1. Нейтральные цвета

| Токен | Значение | Назначение |
|---|---:|---|
| `neutral/950` | `#151922` | самый темный текст, подложка, тень |
| `neutral/900` | `#1D2330` | основной темный фон системных меню |
| `neutral/800` | `#293241` | плотная графитово-синяя поверхность |
| `neutral/700` | `#39475A` | hover-поверхность |
| `neutral/500` | `#7F8DA3` | вторичный текст на светлых предметных экранах |
| `neutral/200` | `#C7D0DD` | светлая обводка и разделители |
| `neutral/100` | `#F0F3F7` | основной светлый текст |

### 4.2. Акцентные цвета

| Токен | Значение | Семантика |
|---|---:|---|
| `amber/500` | `#E4A63A` | деньги, текущая/выбранная локация, важное действие |
| `coral/500` | `#D87468` | отношения, социальный акцент, предупреждение |
| `teal/500` | `#4FA7A0` | информация, телефон, спокойные системные действия |
| `green/500` | `#71A36F` | успех, доступность, нормальное состояние |
| `violet/500` | `#8F78B8` | энергия, особый ресурс или вторичный акцент |
| `red/500` | `#B9544F` | ошибка, запрет, критическое состояние |

Цвет не должен быть единственным способом различить состояние: используются также форма, рамка, насыщенность, подпись или пиктограмма.

### 4.3. HUD-поверхности

| Токен | Значение | Назначение |
|---|---:|---|
| `hud/surface/default` | `#293241A8` | базовое дымчатое стекло |
| `hud/surface/hover` | `#39475AE6` | hover |
| `hud/surface/selected` | `#355B66E6` | выбранный элемент |
| `hud/surface/disabled` | `#29324166` | недоступный элемент |
| `hud/border/default` | `#C7D0DD66` | тонкая нейтральная граница |
| `hud/text/primary` | `#F0F3F7` | основной текст |
| `hud/text/secondary` | `#C7D0DD` | подписи |
| `hud/text/disabled` | `#9AA6B899` | недоступный текст |

HUD не использует большие чисто-белые, пудровые или чисто-черные непрозрачные карточки.

## 5. Типографика

Основной целевой шрифт интерфейса: **Noto Sans** после включения проверенного комплекта файлов в проект. До технического подключения допустим единый временный fallback, но смешивание нескольких гарнитур на одном интерфейсе запрещено.

Рекомендуемые веса:

- Regular — вторичный текст;
- Medium — основной UI-текст и подписи;
- SemiBold — заголовки и важные значения.

Декоративный шрифт не вводится без отдельной необходимости.

### 5.1. Шкала

| Стиль | Размер | Вес | Использование |
|---|---:|---|---|
| `Display/Location` | 24 px | SemiBold | название локации |
| `Title/Section` | 20 px | SemiBold | заголовки секций |
| `Body/Primary` | 18 px | Medium | основные кнопки и действия |
| `Body/Secondary` | 16 px | Regular | ресурсы и дополнительная информация |
| `Label/Tile` | 15 px | Medium | подписи HUD-плиток |
| `Caption` | 13 px | Regular | время, стоимость, причины блокировки, tooltip |

Минимальный постоянный текст интерфейса на базе 1920×1080 — **13 px**.

Длинная русская подпись переносится или сокращается осмысленно; размер шрифта не уменьшается ниже шкалы только ради того, чтобы текст влез.

## 6. Два семейства графики

Чтобы интерфейс не выглядел собранным из разных наборов, графика разделяется на два четких семейства.

### 6.1. Предметные полноцветные изображения

Используются для:

- переходов по локациям;
- действий;
- портретов NPC;
- верхних крупных системных кнопок;
- предметов инвентаря;
- одежды;
- отдельных приложений телефона, если нужен предметный стиль.

Правила:

- прозрачный фон;
- единая перспектива внутри одного класса;
- единое направление света;
- сопоставимая насыщенность и контраст;
- сопоставимая степень детализации;
- объект не содержит собственной нарисованной рамки, круга, квадрата или кнопки, если это не часть самого предмета;
- контейнер и состояния принадлежат UI-компоненту, а не картинке объекта;
- объект центрируется по визуальной массе, а не механически по bounding box.

### 6.2. Functional Icons

Используются для:

- денег;
- энергии;
- времени;
- настроения и эффектов;
- характеристик;
- отношений;
- закрытия/назад;
- подтверждения;
- предупреждения;
- длительности и стоимости действия;
- сортировки, фильтра, навигации и системных команд.

Правила:

- простая читаемая векторная форма;
- единая толщина линий;
- одинаковый optical weight;
- без случайных эмодзи и символов вроде `◇`, `◆`, `✦`, `●`, если существует штатная пиктограмма;
- базовый размер пиктограммы: `24 px`;
- компактный вариант: `16–20 px`;
- крупный вариант для карточек: `32 px`;
- цвет задается семантическим токеном интерфейса.

## 7. Стандарт HUD-медальонов

### 7.1. Top Medallion

Назначение: Настя, Маша, телефон, инвентарь, гардероб, меню и другие постоянные верхние кнопки.

- внешний контейнер: **68×68 px**;
- форма: всегда круглая;
- safe area предметного изображения: ориентир **52×52 px**;
- минимальное внутреннее поле до края круга: **8 px**;
- подпись под кнопкой: `Label/Tile`, обычно 13–15 px;
- все элементы верхнего ряда имеют одинаковый внешний размер вне зависимости от формы картинки внутри;
- прямоугольное изображение не получает отдельную прямоугольную плашку внутри круга;
- значимая часть объекта не должна случайно обрезаться окружностью.

### 7.2. World Tile

Назначение: локации, действия и NPC в основном игровом пространстве.

- внешний контейнер: **104×104 px**;
- форма контейнера: всегда круглая;
- safe area изображения: ориентир **80×80 px**;
- минимальное внутреннее поле: **12 px**;
- подпись: `Label/Tile`, 15 px;
- дополнительная строка: `Caption`, 13 px;
- локации, действия и NPC используют одинаковую геометрию контейнера, но могут различаться семантикой selected-акцента;
- объект не выходит за визуальную границу медальона, если только специальный эффект выхода за рамку не утвержден для всего семейства.

### 7.3. Масштаб внутри медальона

Нельзя масштабировать ассет только по его полному canvas. Сравнивается **визуальный размер главного объекта**.

Пример: изображение телефона и изображение человека должны казаться одинаково уверенно вписанными в свои медальоны, даже если их исходные пропорции различаются.

## 8. Состояния интерактивных элементов

Для повторно используемого интерактивного компонента должны поддерживаться:

- `idle` — обычное состояние;
- `hover` — усиление поверхности/обводки и допустимое легкое приближение;
- `pressed` — краткое уменьшение или смещение;
- `selected` — акцентное кольцо/рамка и стабильное выделение;
- `disabled` — снижение насыщенности и контраста без полного исчезновения;
- `focus` — видимый keyboard-focus.

Только изменение цвета текста не считается полноценным состоянием.

### 8.1. Ассеты состояний

Предпочтительная архитектура для новых элементов:

**один основной полноцветный ассет объекта + универсальные состояния контейнера**.

Не следует создавать четыре почти одинаковых изображения предмета для `idle/hover/selected/disabled`, если состояние можно корректно получить общим UI-компонентом.

Существующий набор раздельных PNG-состояний может сохраняться до отдельной технической миграции; это не повод копировать подход в новые ассеты.

## 9. Основной HUD

### 9.1. Верхняя левая группа

Содержит:

- деньги;
- энергию;
- временные состояния/эффекты.

Ориентир:

- позиция от `(24, 24)`;
- ширина до `240 px`;
- высота около `104–105 px`.

Для денег и энергии используются functional icons, а не буквенные заглушки `₽`/`Э` как самостоятельные графические элементы финального UI.

Временные состояния должны выводиться системой эффектов, а не постоянной захардкоженной строкой «Нормальное состояние».

Под ресурсами, от (24, 140), располагается компактный ряд functional icons (28 px, интервал 4 px) только критических/пиковых состояний и установленных persistent items. На параметр — максимум один значок; hover/focus показывает название и краткое описание. Пороги и состав принадлежат [HUD_TEMPORARY_EFFECTS_SPEC.md](HUD_TEMPORARY_EFFECTS_SPEC.md). HUD не хранит собственные is_tired/has_plug и не выводит промежуточные состояния.

### 9.2. Верхняя центральная группа

Содержит постоянные Top Medallion.

- элементы не объединяются широкой непрозрачной полосой;
- между медальонами сохраняется одинаковый интервал;
- порядок постоянных функций остается стабильным;
- недоступный элемент сохраняет свое место и показывает disabled-state.

### 9.3. Верхняя правая группа

Содержит:

- время;
- день недели и дату;
- текущую локацию;
- период дня;
- короткую дополнительную информацию при необходимости.

Ориентир ширины: `260 px` с допустимым расширением для длинного русского названия локации.

Высота — 104 px от y=24, с компактными внутренними отступами. Базовая композиция двухуровневая: в первой строке крупное время слева и день недели справа, во второй — локация слева и период дня справа. Значения образуют две цельные строки, а не четыре разрозненных угла. Блок NPC начинается не выше y=155 и не пересекается с панелью.

### 9.4. Нижние переходы

- располагаются слева вдоль нижнего края;
- текущая локация показывается только в верхней правой панели, отдельной нижней плитки нет;
- далее идут доступные переходы;
- подпись и время пути не зашиваются в изображение;
- по решению владельца от 7 сентября 2026 переходы занимают **только левую половину экрана**, действия — **только правую**, оба меню в один ряд без прокрутки;
- при 1920×1080 рабочая ширина каждого меню — 912 px: слева x=24…936, справа x=984…1896; начало рядов y=892;
- подписи компактные: 13 px, до трех строк в 54 px, центрированы относительно медальона в общей фиксированной ячейке. Полное название, время и причина блокировки доступны только по hover/focus; постоянных строк времени нет;
- сначала экономятся интервалы и подписи, группируются родственные переходы; текущие наборы помещаются с кругом 104×104 px. Размер не должен создавать пересечение с соседней половиной;
- переходы на соседние этажи одного здания объединяются в **один круг, разделенный по горизонтали**: верхний полукруг — вверх, нижний — вниз. Каждый полукруг имеет собственные hit area, hover/focus и disabled-state;
- отсутствующее или закрытое направление неактивно. Группировка использует только реальные переходы карты, не создает новых маршрутов;
- в жилом доме подвал и крыша входят в тот же вертикальный ряд. Переход из двора в подъезд остается обычной плиткой, а не этажной кнопкой.

### 9.5. Нижние действия

- располагаются в правой половине вдоль нижнего края, в один ряд без прокрутки;
- имеют ту же геометрию World Tile;
- краткая подпись задается централизованно с fallback к названию действия; полное название, длительность и причина блокировки доступны по hover/focus;
- однозначное детерминированное действие выполняется сразу по нажатию; компактная контекстная панель появляется только для реального выбора варианта, параметра, цели/предмета или особого подтверждения;
- раскрытие действий не должно хаотично сдвигать остальные HUD-элементы.

Во время персонажной реплики или авторского текста нижние переходы, действия и их контекстная панель исключаются из render/focus tree. Их заменяет полноширинная нижняя dialogue-панель. После текста свободное управление восстанавливается. Доступный SideImage используется для персонажа; отсутствие изображения и авторский текст не резервируют пустое место под портрет.

Системный `notify` центрирован по x под верхними медальонами, y=132. Он сообщает новое событие или изменение состояния, автоматически исчезает и не дублирует название текущей локации, постоянно видимое в HUD. Короткие и длинные сообщения не перекрывают ресурсную и временную панели.

### 9.6. NPC

Присутствующий NPC отображается цветным портретным World Tile. Выбор NPC раскрывает доступные социальные действия единым компактным строчным списком: небольшая тематическая иконка слева, текст справа, общие hover/focus/disabled-состояния. Крупные круглые World Tile внутри списка действий NPC не используются.

Текстовые кнопки вида `● Название действия` допустимы как прототип, но не как финальный вид: используются штатная пиктограмма/компонент действия и нормальная типографика.

## 10. Панели и модальные окна

Общая модальная система используется для профилей, служебных окон и тех экранов, которые не имеют собственной предметной оболочки.

### 10.1. Modal Shell

- затемнение фона нейтральным полупрозрачным слоем;
- максимальная рабочая область не перекрывает края экрана;
- крупная панель использует единый радиус и padding;
- заголовок слева, закрытие справа;
- закрытие использует functional icon, а не текстовый `×` как финальное решение;
- вложенные панели не должны создавать эффект «карточка внутри карточки внутри карточки» без функциональной причины.

### 10.2. Button

Минимальные состояния: idle, hover, pressed, disabled, focus.

- текст — `Body/Primary` или `Body/Secondary`;
- горизонтальный padding обычно 16–24 px;
- вертикальный padding обычно 8–12 px;
- одна экранная группа использует одинаковую высоту кнопок.

### 10.3. Настройка для родственников (удалена)

Отдельного переключателя для родственников в настройках игры нет: механика родства удалена 2026-10-29 (см. `RELATIONSHIPS_INVENTORY_WARDROBE_SPEC.md` §3.2).

## 11. Карточки персонажей

Карточки Насти, Маши и других персонажей должны использовать общую структуру, но содержимое определяется каноном конкретного персонажа.

Общие правила:

- портрет/изображение персонажа занимает визуально значимую область;
- рядом выводятся игровые характеристики, отношения или доступная игроку информация;
- характеристики используют functional icons одного семейства;
- временные технические символы `◇`, `●`, `✦`, `◆` заменить штатными пиктограммами;
- не отображать захардкоженную биографическую, учебную или рабочую информацию, если она может изменяться в игровом состоянии;
- не дублировать на карточке сведения, которые еще не известны игроку;
- отношения не сводить к одной старой строке `Отношения: Дружеское/Партнер`: постоянная связь/родство, social state и intimacy state показываются раздельно только в уместном объеме и без спойлера будущих routes.

Approved visual reference карточки Насти задает общую композиционную схему, но текст и данные на нем не являются каноном.

## 12. Телефон

Телефон имеет собственную предметную оболочку современного смартфона.

### 12.1. Геометрия

- визуально правдоподобный современный корпус;
- единый радиус внешнего корпуса и экрана;
- безопасные поля сверху и снизу;
- статусная строка;
- экран телефона не должен выглядеть обычным Ren'Py modal window с нарисованной рамкой вокруг.

### 12.2. Приложения

- приложения используют единый набор иконок;
- домашний экран — регулярная сетка;
- сообщения, контакты, календарь, задания, банк и другие реализованные приложения используют общие внутренние компоненты списков и заголовков;
- placeholder не маскируется под завершенное приложение;
- системная нижняя навигация телефона использует одинаковые functional icons и состояния;
- обои могут меняться отдельно от функциональной геометрии.

Визуальное сходство с современным iPhone допускается как направление, но проект не зависит от внешней iOS/Figma-библиотеки.

Approved visual reference телефона задает композицию корпуса, домашнего экрана и общего характера приложений, но не требует копирования конкретных иконок или устаревших подписей.

### 12.3. Приложения телефона (утверждено в TASK-009)

Уточнение при приемке: затемнение мира идентично `modal_shell` гардероба, включая полный размер и hover. Внутренние приложения сохраняют выбранные обои телефона вместо непрозрачной серой подложки; карточки, кнопки, календарные ячейки и пузырьки используют скругленные полупрозрачные фиолетовые/бирюзовые поверхности с тонкой светлой рамкой. Вкладки заданий центрированы и полужирные. Карточка задания разделяет заголовок/описание и строки целей с read-only отметками completed/pending из quest state; UI не завершает цели нажатием.

В чате нижняя кнопка раскрывает/сворачивает меню доступных реплик поверх истории. В закрытом состоянии варианты скрыты; бытовые «Как дела?», «Что делаешь?», «Ты где?» и сюжетные варианты используют один список. Переход в другой экран и успешная отправка закрывают список. Отсутствие утвержденных ответов/cooldown сохраняет disabled-state внутри меню.

Поверхности телефона: glass `#51436B` 82%, hover `#6F5C8A` 94%, accent `#397D79` 94%, menu `#393044` 98%; рамка `#EEE2D1` 24%, радиус 18 px. Это производные фиолетового/бирюзового направления общей палитры; иконки и корпус, принятые владельцем, сохраняются.

`phone_screen` владеет только общей предметной оболочкой; home, contacts/contact card, quests/quest card, calendar, messages/chat — самостоятельные компоненты. Единые status bar, безопасные поля, functional icons home/back/close и геометрия сохраняются при переходах. Контакты без поиска: аватар, доступное имя, связь; карточка показывает только известные факты и разрешенные отношения/характеристики, действия «Позвонить» и «Написать». Звонок без определенной механики недоступен с объяснением; «Написать» открывает чат контакта.

Задания фильтруются по `active/completed/failed`; строка содержит название без повторного статуса, карточка — существующие описание, этапы, условия и сроки. Все цели одного задания собраны в один checklist-контейнер с компактными строками и read-only checkbox, без отдельной крупной карточки на каждую цель. Календарь показывает месячную сетку с переключением без изменения игрового времени, выделяет выходные/сегодня/известные события. Hover/focus даты с событием обновляет устойчивое выбранное событие; обычная дата не очищает выбор. Карточка события прокручивается только при фактическом overflow, а при одном коротком событии scrollbar отсутствует. Источник данных — TIME_ACTIONS_QUESTS_EVENTS_SPEC.

## 12.4. Системные меню Ren'Py

- game-menu screens используют цельный полноэкранный `neutral/900` фон без старых декоративных полос и коричневых подложек;
- панели, слоты, confirm и empty-state используют централизованные neutral/menu surfaces, сохраняя teal/amber как семантические акценты;
- confirm собирается общими стилями и не зависит от отсутствующего растрового frame-asset;
- весь player-facing текст стандартных меню, quick menu, подтверждений и save/load — русский;
- метаданные сохранений используют локал-независимый цифровой формат даты и не меняют timestamp сохранения.

Сообщения: список существующих чатов с аватаром, именем, последней репликой и unread; отдельный хронологический чат с выбором доступных реплик, без свободного ввода. Сохраняется выбор обоев. Банк использует ту же оболочку и общие компоненты: показывает баланс, сводку, историю и утвержденные долговые операции из единого wallet, без второй базы финансов. Будильник — отдельное приложение общей оболочки телефона: в первой версии позволяет задать время `HH:MM`, включить или отключить один одноразовый будильник и показать его текущее состояние; правила пробуждения задаются только `SLEEP_ALARM_SPEC.md`. Камера/галерея/карта остаются недоступными приложениями; существующие внешние unlock-интеграции не удаляются. Финансовые правила задаются только `ECONOMY_BANKING_SPEC.md`.

## 13. Инвентарь

- внешняя предметная оболочка — раскрытая цветная коробка;
- функциональная часть — регулярная сетка;
- базовая ячейка едина для расходуемых, постоянных и квестовых предметов;
- предмет на прозрачном фоне занимает единый safe area;
- количество показывается небольшим бейджем;
- выбранный предмет получает увеличенное изображение, название, описание и доступные действия;
- категории меняют содержимое, а не геометрию окна;
- пустая ячейка имеет спокойное состояние без декоративного шума.

Approved visual reference инвентаря задает предметную оболочку коробки и композицию `сетка + карточка выбранного предмета`.

## 14. Гардероб

- декоративный фон — открытый шкаф;
- слева — зеркало/область персонажа;
- справа — сетка одежды;
- нарисованные полки не управляют фактическими координатами элементов;
- категории одежды используют одну сетку;
- надетая вещь имеет selected-state;
- недоступная вещь остается видимой, если игроку полезно понимать ее существование, и показывает причину недоступности;
- рабочий гардероб использует те же компоненты сетки и ячеек, меняя оболочку и фильтр.

Approved visual reference гардероба задает композицию `зеркало + открытый шкаф + сетка одежды`, но не фиксирует конкретные предметы одежды, подписи и данные.

## 15. Ячейки предметов и одежды

Для сеток инвентаря, магазина и гардероба используется единая логика геометрии.

Базовый ориентир ячейки на 1920×1080: **160–168 px**.

Внутри:

- изображение: safe area около `112–120 px`;
- подпись не встраивается в само изображение;
- количество/статус — отдельный бейдж;
- selected обозначается рамкой/поверхностью, а не изменением исходного ассета;
- предметы разных пропорций нормализуются по визуальной массе.

## 16. Tooltips и служебная информация

Tooltip/контекстная карточка может показывать:

- название;
- краткое описание;
- время;
- стоимость энергии;
- денежную стоимость;
- причину недоступности.

Не показывать одновременно все поля, если они не относятся к объекту.

Tooltip не заменяет постоянную подпись у элемента, если без подписи объект трудно распознать.

## 17. Визуальная иерархия

На одном экране должно быть очевидно:

1. где игровой мир;
2. где постоянные ресурсы и системные функции;
3. где навигация;
4. где доступные действия;
5. что выбрано;
6. что недоступно;
7. где временная контекстная информация.

Не использовать одинаково яркий акцент одновременно для большого количества элементов.

## 18. Проверка читаемости

Каждый новый постоянный HUD-компонент проверяется минимум на пяти типах фонового изображения:

1. светлая комната;
2. темная комната;
3. насыщенная цветная локация;
4. дневная улица;
5. сцена с персонажем в центральной области.

Проверяются:

- читаемость текста;
- различимость цветных ассетов;
- видимость границ;
- сохранность центральной композиции;
- idle/hover/pressed/selected/disabled/focus;
- длинные русские подписи;
- 6+ переходов или действий;
- масштабирование интерфейса на реальном запуске Ren'Py.

Если компонент хорошо выглядит на однотонном тестовом фоне, но теряется на реальной локации, он считается недоработанным.

## 19. Правила производства графических ассетов

Перед созданием серии ассетов определяется ее класс: Top Medallion, World Tile, functional icon, item/wardrobe thumbnail или крупная предметная оболочка.

Для серии заранее фиксируются:

- canvas;
- safe area;
- прозрачный/непрозрачный фон;
- ракурс;
- направление света;
- степень реалистичности;
- насыщенность;
- правила обрезки;
- визуальный масштаб.

Нельзя создавать набор «по одной картинке как получится», а потом пытаться выровнять его внутри Ren'Py.

### 19.1. Проверка серии

Перед включением нового набора минимум 6 разных элементов ставятся рядом на одном тестовом листе. Проверяется:

- одинаковый визуальный масштаб;
- одинаковые поля;
- единая стилистика;
- отсутствие случайных внутренних рамок;
- отсутствие элементов, которые визуально вываливаются из контейнера;
- читаемость на реальном HUD-размере, а не только в увеличении.

## 20. Единый источник токенов в реализации

`docs/systems/UI_VISUAL_SYSTEM_SPEC.md` задает правила и значения.

В игровом коде должен существовать один технический слой дизайн-токенов/стилей, через который получают оформление остальные экраны.

Требования к реализации:

- не дублировать палитру в нескольких `.rpy`;
- не хранить системные размеры одновременно в разных screen-блоках;
- по возможности использовать общие компоненты вместо копирования разметки;
- локальный override допустим для уникальной композиции, но не должен превращаться в новую параллельную дизайн-систему;
- старые стили и ассеты после подтвержденной миграции удаляются, если больше нигде не используются.

Текущий `game/ui/design_system.rpy` рассматривается как техническая реализация этой системы и должен постепенно синхронизироваться с настоящим документом через TASK/Codex. Сам код не становится конкурирующим источником дизайнерских решений.

## 21. Приоритет доработки существующего UI

При ревизии текущего интерфейса соблюдать порядок:

1. унифицировать токены, базовые стили и повторно используемые компоненты;
2. привести существующие HUD-ассеты к стандартам Top Medallion и World Tile;
3. заменить буквенные, Unicode- и текстовые графические заглушки functional icons;
4. привести карточки персонажей к общему шаблону;
5. закончить предметную оболочку телефона;
6. закончить коробку-инвентарь;
7. закончить шкаф-гардероб;
8. по мере появления новых систем применять уже готовые компоненты к магазину, транспорту, университету и другим экранам.

Не следует сначала рисовать большой объем новых иконок, пока не закреплены контейнер, safe area и общий способ отображения состояний.

## 22. Definition of Done для нового UI-компонента

Компонент считается визуально завершенным, если:

- он следует токенам этого документа;
- использует правильное семейство графики;
- имеет необходимые интерактивные состояния;
- не использует временные текстовые/Unicode-заглушки;
- сохраняет читаемость на реальных игровых фонах;
- не ломает центральную безопасную область;
- корректно работает с длинным русским текстом;
- повторно использует общие компоненты там, где это возможно;
- не требует внешнего платного дизайнерского сервиса для дальнейшей поддержки;
- проверен непосредственно в Ren'Py.

## Интеграция TASK-008

Вкладка «Интимное» — фильтр единого inventory, без отдельного хранилища. Костюмы отображаются в гардеробе, массажное масло — среди обычных расходников. Установленный предмет не дублируется: маркер «Установлен», команда «Вынуть»; неустановленный persistent item — «Вставить». Action tools выбираются через совместимое действие.

Существующая композиция гардероба сохраняется; он открывается только в разрешенных точках и сценарных контекстах. Домашняя/рабочая точка не создает отдельной системы. Будущий окончательный UX по Bright Past, presets/outfits и новые вкладки гардероба не утверждаются в рамках TASK-008.
