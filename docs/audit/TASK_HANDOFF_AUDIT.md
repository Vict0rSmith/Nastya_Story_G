# TASK Handoff Audit — Progression Gate

**Дата:** 2026-09-05  
**Статус:** рабочий вывод аудита; не является отдельным источником игрового канона.

## Цель проверки

Проверить фактический путь исполнителя от получения TASK до чтения художественных правил и определить, где надежнее всего активировать In-game Progression Gate, не распространяя его на обычное проектное обсуждение.

## Проверенный контур

Проверены актуальные:

- `docs/MASTER_SPEC.md`;
- `docs/DEVELOPMENT_WORKFLOW.md`;
- `docs/tasks/README.md`;
- `docs/templates/TASK_TEMPLATE.md`;
- `AGENTS.md`;
- реальные TASK разных поколений/стадий:
  - `docs/tasks/review/TASK-004_unpack_luggage_and_grooming.md`;
  - `docs/tasks/ready/TASK-006_relationship_model_and_incest_selector.md`;
  - `docs/tasks/done/TASK-003_sync_minimal_starting_wardrobe.md`;
- каталоги `ready`, `in_progress`, `review`, `done`.

## H-001 — фактическая цепочка нового TASK уже подходит для Progression Gate

Текущий workflow требует перед технической реализацией прочитать `AGENTS.md` и `MASTER_SPEC.md`; при работе по TASK — также `DEVELOPMENT_BOARD`, сам TASK и его Context Manifest.

Если реализация создает/существенно редактирует игровой текст, workflow и TASK template требуют открыть `ADULT_EROTIC_TONE_GUIDE.md`, `DIALOGUE_WRITING_GUIDE.md` и карточки реально участвующих персонажей.

Следовательно, для современного TASK естественная цепочка уже существует:

`TASK → Context Manifest → READ REQUIRED → Adult Erotic Tone Guide → художественные ограничения реализации`.

Новый отдельный глобальный гайд только ради включения Progression Gate не нужен.

## H-002 — TASK должен передавать контекст gate, но не владеть лестницей

Саму визуальную лестницу/значение уровней не следует копировать в каждый TASK. Основной художественный владелец остается `ADULT_EROTIC_TONE_GUIDE.md`.

TASK должен сообщить исполнителю только конкретный контекст реализации, необходимый для применения канона, например:

- затрагивает ли TASK новый/редактируемый игровой текст;
- стадия/условия сцены, если они не однозначно следуют из канонической сцены;
- применен ли отдельный scripted content override;
- точный канонический источник сцены/события.

Так TASK остается единицей реализации, а не вторым источником художественной механики.

## H-003 — реальный TASK-006 подтверждает работоспособность Context Manifest

`TASK-006` уже содержит полноценный `Context Manifest` и включает `ADULT_EROTIC_TONE_GUIDE.md` в `READ REQUIRED`, поскольку задача затрагивает интимную/сексуальную системную область. `DIALOGUE_WRITING_GUIDE.md` оставлен в `READ IF NEEDED`, поскольку видимый литературный текст почти не меняется.

Это хороший пример контекстной экономии: исполнитель получает Erotic Guide там, где он нужен, не загружая Dialogue Guide без необходимости.

## H-004 — старые TASK показывают проблему обратной совместимости процесса

`TASK-003` и `TASK-004` созданы до нынешнего обязательного Context Manifest и не содержат полноценного раздела `Context Manifest` по текущему шаблону.

`TASK-004` затрагивает каноническую сцену и интимный grooming-контент, но его собственные `related_specs`/`related_entities` не включают `ADULT_EROTIC_TONE_GUIDE.md`; он лишь ссылается на `DIALOGUE_WRITING_GUIDE.md` в требованиях к сцене. Если исполнитель ориентировался бы только на старый TASK, художественный контекст был бы неполным.

Сейчас это частично страхуется более новым `AGENTS.md` и `DEVELOPMENT_WORKFLOW.md`, которые независимо от возраста TASK требуют читать оба content guide при создании/существенной редактуре игрового текста.

**Вывод:** Progression Gate нельзя делать зависимым только от наличия специального поля в конкретном TASK. Нужен обязательный workflow-level trigger, а TASK/Manifest должен конкретизировать контекст.

## H-005 — формула «TASK включает gate» требует одного уточнения из-за прямых поручений

Репозиторий разрешает техническую реализацию без формального TASK по прямому поручению владельца. Для такого режима `AGENTS.md` и `DEVELOPMENT_WORKFLOW.md` все равно требуют обязательные content guides, если создается/редактируется игровой текст.

Поэтому точная операционная формула:

**In-game Progression Gate активируется при переходе в режим реализации фактического игрового контента. Формальный TASK является основным и наиболее явным handoff-механизмом, но прямое техническое поручение владельца активирует тот же режим без создания TASK.**

До этого перехода — обсуждение, анализ, идеи, варианты, тестовые примеры, аудит — In-game Progression Gate не влияет на выводы и степень рассматриваемой визуальной откровенности.

## H-006 — лучше не вводить обязательное числовое/ранговое поле в каждый TASK

Отдельное поле вроде `progression_rank: modest` во frontmatter каждого TASK выглядит удобным, но создает риск:

1. дублировать состояние, которое уже определяется канонической сценой/датой/системой;
2. получить рассинхронизацию TASK и канона;
3. заставить чисто технические TASK заполнять нерелевантное поле;
4. снова создать ложную связь `rank = вся допустимая визуальность`.

Предпочтительнее условный раздел/подраздел **только для TASK, который создает или существенно меняет игровой контент**. Он должен не копировать лестницу, а фиксировать применимый контекст и override.

Рабочее название: `Content Authoring Context` / `Контекст игрового контента`.

Минимальная логика:

- если TASK только переносит уже утвержденный литературный текст дословно — сохранить его существующую степень откровенности; новый progression-расчет не должен самовольно санитизировать утвержденный текст;
- если TASK создает/существенно редактирует новый игровой текст — прочитать Erotic Guide и определить применимый In-game Progression Gate из канонического состояния сцены;
- если сцена имеет утвержденный scripted override — TASK должен явно на него сослаться;
- если необходимый progression context нельзя однозначно получить из канона — не угадывать, вернуть проектный вопрос владельцу до реализации.

## H-007 — рекомендуемая точка будущего изменения

После завершения общего writing-аудита наиболее надежная архитектура выглядит так:

1. **`ADULT_EROTIC_TONE_GUIDE.md`** — единственный художественный владелец определения In-game Progression Gate, визуальной лестницы и scripted override.
2. **`DEVELOPMENT_WORKFLOW.md` / `AGENTS.md`** — определяют момент активации: начало реализации фактического игрового контента, по TASK или прямому поручению.
3. **`TASK_TEMPLATE.md`** — при TASK с новым/существенно редактируемым игровым текстом заставляет передать исполнителю конкретный Content Authoring Context и включить Erotic Guide в `READ REQUIRED`.
4. **конкретный TASK** — не повторяет лестницу; содержит только конкретные входные данные/ссылки/override для данной реализации.
5. **QA/Implementation report** — проверяет, что применен правильный контекст и исполнитель не добавил ни самовольную санитизацию, ни самовольное повышение откровенности.

## H-008 — практический вывод по текущему репозиторию

Нынешняя архитектура уже почти готова для такого разделения. Главная проблема не в отсутствии маршрута к Erotic Guide, а в том, что:

- сам Erotic Guide пока недостаточно явно отделяет проектное обсуждение от authoring фактической игры;
- текущий TASK template не передает отдельным компактным блоком progression/override context;
- старые TASK не всегда соответствуют новому Manifest-процессу, поэтому обязательный trigger должен страховаться workflow/AGENTS, а не только шаблоном TASK.

До окончания общего writing-аудита основные файлы не изменяются.
