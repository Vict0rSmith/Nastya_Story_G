# Nastya Story — Development Workflow

## Назначение

Этот документ задает рабочий контур разработки: как проектные решения переходят в реализацию, как выбирается исполнитель, как уменьшается контекст, выполняются проверки и поддерживается оперативный план.

Он **не является источником канона** игровых механик, мира, персонажей, сюжета, UI или художественной эротической установки. Канон находится в профильных файлах `docs/systems/`, `docs/world/` и `docs/content/`; единственным каноническим источником топологии мира, вложенности пространств и направлений переходов является [`graphs/map.drawio`](graphs/map.drawio).

Если какой-то фрагмент не получается выполнить, на его месте ставится `[TODO: что здесь должно быть]`, а остальная работа продолжается на том же уровне (см. [`../AGENTS.md`](../AGENTS.md) §0).

## Рабочие уровни

Используются четыре разных уровня:

1. **Каноническая спецификация** — что должно существовать и как должно работать.
2. [`IMPLEMENTATION_ROADMAP.md`](IMPLEMENTATION_ROADMAP.md) — сводный статус реализации систем и крупных направлений.
3. [`DEVELOPMENT_BOARD.md`](DEVELOPMENT_BOARD.md) — оперативная панель текущего фокуса, активных TASK, review, очереди и блокеров.
4. **TASK** — формализованная единица реализации с критериями приемки и Context Manifest.

TASK не является единственным способом дать поручение. Владелец может напрямую поручить любому ИИ-исполнителю (Grok Bot, ChatGPT, Codex и другим) конкретную работу. Прямое поручение не становится отдельным источником канона: оно исполняется в рамках актуальных спецификаций, а утвержденное изменение канона синхронизируется с основным источником.

При расхождении канонической спецификации, Roadmap/Board/TASK и реализации приоритет имеет актуальный канон, если владелец прямо не утвердил новое решение.

## Два способа начать реализацию

### Работа по TASK

Используется для формализованных задач с жизненным циклом `backlog → ready → in_progress → review → done`, критериями приемки и Context Manifest.

### Прямое поручение владельца

Используется, когда владелец напрямую просит исправить, реализовать, перенести, дописать, проверить или иным образом изменить конкретную часть проекта.

- Не требуется создавать TASK для каждой локальной команды.
- Поручение задает начальные границы, но не отменяет `AGENTS.md`, канон и проверки.
- Если работа требует новых неутвержденных продуктовых/архитектурных решений, сначала уточняются именно эти решения.
- Сам по себе многофайловый объем не означает автоматическую передачу Codex.
- Если поручение меняет активную работу или статус системы, проверить Board/Roadmap.

## Исполнители

ChatGPT и Codex являются **двумя исполнителями одного рабочего процесса**. Оба могут выполнять TASK и прямые поручения, изменять документацию, игровой текст и код в пределах утвержденной задачи.

Выбор исполнителя определяется практикой:

- доступными инструментами;
- размером и открытостью области работы;
- необходимостью локальной диагностики;
- стоимостью/удобством контекста;
- прямым выбором владельца.

ChatGPT обычно удобен для проектирования, канона, контента и контролируемых через GitHub локальных/средних либо ограниченных многофайловых изменений. Codex особенно полезен для крупных открытых изменений, сложного рефакторинга, длительного исследования кодовой базы и интенсивного локального диагностического цикла.

Нельзя автоматически назначать Codex только потому, что работа касается `.rpy`, UI/runtime, нескольких файлов или потому что локальный компьютер недоступен ChatGPT. Уровень проверки определяется фактически доступными средствами, а не именем исполнителя.

## Обязательный цикл перед реализацией

Перед технической работой ИИ-исполнитель:

1. использует актуальный GitHub/`origin/main` как источник текущего состояния; локальный исполнитель дополнительно выполняет безопасную Git-проверку по `AGENTS.md`;
2. читает `AGENTS.md` и `docs/MASTER_SPEC.md`;
3. определяет источник поручения:
   - TASK → читает `DEVELOPMENT_BOARD.md`, TASK и его Context Manifest;
   - прямое поручение → использует формулировку владельца как границу и открывает тематический MOC, обязательные источники и нужные файлы реализации;
4. если работа затрагивает состав карты, вложенность пространств или направления переходов, обязательно открывает актуальный `docs/graphs/map.drawio`;
5. проверяет существующую реализацию до изменений;
6. расширяет контекст только при обнаружении реальной зависимости.

Запрещено рекурсивно читать весь `docs/` или `game/` «для понимания проекта», если конкретная работа этого не требует.

## Handoff игрового текста

Любая работа с игровым текстом начинается с [`content/WRITING_BRIEF.md`](content/WRITING_BRIEF.md). Режимов два:

- **Пишу текст игры** — создание, дописывание или заметная художественная правка. TASK и прямое поручение владельца равноправны. Путь: карточка сцены → черновик → проверка из 5 пунктов ([`content/STYLE_CHECKLIST.md`](content/STYLE_CHECKLIST.md)). Порядок загрузки задает бриф; длинные гайды — по нужде.
- **Переношу утвержденный текст** — дословно: факты, голос, регистр и уровень откровенности не меняются. Если нужна заметная правка — это уже первый режим.

Обсуждение идей и вариантов лестницей откровенности не ограничивается; канон, «кто что знает», физика и характер действуют всегда.

## Интимный/эротический контент внутри реализации

Правила одинаковы для всех исполнителей и действуют, даже когда текст — лишь часть `.rpy`-работы. Главное — в [`content/WRITING_BRIEF.md`](content/WRITING_BRIEF.md):

- общие границы слоя — `content/WRITING_BRIEF.md` §3 п. 1;
- внутри границы — без самоцензуры и без увода главного за кадр;
- бытовую сцену не делать эротической для героев без причины; смысл для героев и взгляд игрока определяются отдельно;
- реакция не переписывает физику;
- лестница откровенности ограничивает только готовый текст, не обсуждение.

## Context Manifest

Каждый новый или существенно переработанный TASK содержит `Context Manifest`:

- **READ REQUIRED** — обязательные канонические документы;
- **CODE REQUIRED** — файлы реализации для проверки до изменения;
- **READ IF NEEDED** — прямые зависимости по условию;
- **DO NOT SCAN** — области, которые не загружаются без причины;
- **CHECKS** — завершающие проверки.

Context Manifest задает минимальный стартовый набор, но не запрещает открыть реально обнаруженную зависимость.

Если TASK создает/существенно редактирует игровой текст, `READ REQUIRED` включает `content/WRITING_BRIEF.md` и карточки участников; длинные гайды и `content/intimate_language/` — только реально нужные. `Content Authoring Context` передает режим, сцену, участников, обязательные факты и ступень, **не копируя художественные гайды или словари**.

Для прямого поручения отдельный Manifest не обязателен: действует та же схема минимального контекста.

Шаблон: [`templates/CONTEXT_MANIFEST_TEMPLATE.md`](templates/CONTEXT_MANIFEST_TEMPLATE.md).

## Два уровня проверки технической реализации

Уровень определяется **фактически доступными средствами**, а не исполнителем.

### `FULL_LOCAL`

Когда доступен локальный Ren'Py SDK/MCP либо эквивалентный контур, по применимости выполняются:

1. Git diff и поиск зависимостей;
2. repository/CI checks;
3. MCP diagnostics;
4. Ren'Py lint;
5. preview/launch/runtime check для видимых или runtime-изменений;
6. при ошибке — исправление и повтор затронутых проверок.

### `REMOTE_LIMITED`

Когда локальный runtime/MCP недоступен:

1. проверить актуальные файлы через GitHub;
2. выполнить доступный статический анализ, поиск ссылок и зависимостей;
3. использовать доступные CI/checks, если они есть;
4. не заявлять о локальном lint/runtime/preview, если они не запускались;
5. перечислить непроведенные проверки в отчете.

## Завершение реализации

### Минимальная достаточная проверка для двух исполнителей

Подробный владелец правил выбора и повторения проверок — [`RENPY_MCP_WORKFLOW.md`, раздел 5](RENPY_MCP_WORKFLOW.md#5-частота-и-объем-проверок). `FULL_LOCAL` означает доступность локального контура, а не обязательный прогон всей игры. Это правило одинаково для Codex и ChatGPT.

- **Codex в рабочей копии:** проверить diff и прямые зависимости; выполнить один lint при изменении `.rpy`, выбранные тесты затронутого поведения и адресный визуальный просмотр измененных экранов. Полные логи хранить в файлах, в контекст возвращать сводку и ошибки.
- **ChatGPT через GitHub:** проверить diff и затронутые контракты; прочитать результаты CI для проверяемого SHA. Если доступен self-hosted runner, выбрать нужные suites/testcases в `Local Ren'Py verify` через `workflow_dispatch`, затем прочитать краткий summary. Для UI открыть только нужные изображения из артефакта, если инструменты позволяют, и проверить наложения, обрезание текста/сеток, видимость и состояния элементов. Успешный job без просмотра кадров не является визуальной проверкой.
- **ChatGPT без доступного runner/артефактов:** сохранить `REMOTE_LIMITED`; по коду проверить измененные ссылки, размеры и ограничения контейнеров, условия видимости и контракты состояния. Это может находить те же классы дефектов, но не гарантирует обнаружение фактического наложения или обрезания при рендере. В отчете назвать конкретный непроверенный экран/поток; не требовать повторной проверки всей игры и не передавать реализацию Codex автоматически.
- Успешный применимый CI-прогон того же состояния кода можно использовать как доказательство без дублирующего локального запуска. Сверить SHA, выбранные тесты, результат и доступность артефактов; `skipped`, очередь, старый SHA или иной набор тестов не означают прохождение текущих критериев.
- После зеленого результата повторять проверки только из-за изменения их входных файлов/зависимостей, новой ошибки или конкретного оставшегося критерия. Правка отчета/доски сама по себе не требует повторного lint/runtime. Для переноса результата между коммитами явно подтвердить отсутствие изменений проверяемого кода и конфигурации.
- Уже прочитанные неизменившиеся источники повторно целиком не загружать; читать diff и нужные фрагменты. Обязательные канонические источники и критерии TASK не отменяются.

Автоматический push-job сохраняет базовый `nastya_runtime`; он не доказывает прохождение TASK-specific проверок. Для конкретной задачи выбирать их явно. Команды и ограничения удаленного запуска описаны в разделе 5 Ren'Py workflow.

Для TASK:

1. выполнить проверки из TASK и Context Manifest;
2. обновить implementation report;
3. перевести TASK в `review`;
4. синхронизировать `DEVELOPMENT_BOARD.md`;
5. после принятия владельцем перевести TASK в `done` и обновить Board/Roadmap, если статус системы изменился.

Для прямого поручения:

1. выполнить применимые проверки;
2. сделать Change Impact Check;
3. синхронизировать реально затронутые документы/код;
4. дать владельцу краткий отчет: что изменено, что проверено, уровень проверки, известные ограничения и commit SHA/PR.

## Обязательная синхронизация после принятия и перед следующей задачей

Правило одинаково для Codex и ChatGPT, TASK и прямых поручений. Принятие владельцем результата (например, «принимаю работу») является разрешением завершить Git-публикацию этой работы без повторного вопроса о push/merge. Перевод TASK в `done` также требует этой процедуры. Не переводить непринятые соседние TASK в `done` ради синхронизации.

1. Зафиксировать принятые изменения, implementation report, статус TASK и Board/Roadmap по применимости. Не включать посторонние незавершенные изменения, saves или тестовые артефакты.
2. Выполнить fetch и сопоставить локальную историю с `origin/main`. Сохранить обе истории; при расхождении использовать обычное слияние с проверкой конфликтов, без reset/rebase/force push. При неясном содержательном конфликте остановиться и назвать блокер.
3. Опубликовать результат в GitHub `main` обычным push либо разрешенным PR/merge-процессом. При branch protection выполнить требуемый маршрут, не обходить защиту. Коммит только локально, push рабочей ветки или открытый PR еще не означают завершенную синхронизацию.
4. Обновить каноническую локальную копию `T:\Nastya_Story_G` до опубликованной `main`: Codex делает это непосредственно; ChatGPT использует доступный `Local safe sync`/локальный runner и проверяет результат. `queued`, `pending`, `skipped`, offline runner и отсутствие доступа — это **SYNC PENDING**, не успех.
5. Подтвердить после fetch: локальная ветка `main`, `HEAD = main = origin/main`, нет незафиксированных проектных изменений. Указать общий SHA и результат применимых CI checks. Локальная команда: `./tools/check_git_sync.ps1 -RepoRoot T:/Nastya_Story_G`. Она ничего не сливает и не публикует; код 1 означает незавершенную синхронизацию.

Если владелец явно просит оставить работу локально/в отдельной ветке, выполнить это исключение и назвать его в отчете. Иначе нельзя завершать принятую работу сообщением «сделано, но не опубликовано» без конкретного блокера.

**Перед следующей реализацией** оба исполнителя проверяют синхронизацию предыдущего результата. Если она не завершена, сразу сообщают: «Не синхронизировано: <причина>. Сначала завершаю Git-синхронизацию, затем приступаю к следующей задаче». Сначала устраняют расхождение в рамках имеющегося разрешения; новую реализацию и перевод следующего TASK в `in_progress` не начинают. Чтение для диагностики/восстановления синхронизации разрешено. Незавершенную непринятую работу не публиковать как принятую: сначала сохранить ее и разрешить блокер с владельцем.

Если ChatGPT не может получить фактический SHA локальной копии, он подтверждает только GitHub-публикацию и явно оставляет локальную синхронизацию неподтвержденной. Принятый TASK в `done` при таком сбое не считается операционно закрытым: в отчете/доске указать `SYNC PENDING` и конкретный блокер до восстановления. Статус `done` не подменяет факт синхронизации.

`Local safe sync` работает для всех push в `main`, независимо от доступности Ren'Py SDK; `Local Ren'Py verify` запускается только по runtime-путям. У workflow отдельные concurrency groups: одна общая группа GitHub могла бы отменять ожидающую runtime-проверку при поступлении sync-job. Единственный runner с меткой `nastya-story` последовательно выполняет задания для общей локальной копии; нельзя подключать второй runner к той же копии без общей блокировки. Автоматический sync только подтягивает опубликованные изменения и не публикует локальные коммиты; публикацию обеспечивает исполнитель.

## Принцип минимальных изменений

Изменять только то, что требуется поручением и реально затронутыми зависимостями. Не использовать локальную задачу как повод для несвязанного рефакторинга, переписывания канона или косметической чистки соседних файлов.
