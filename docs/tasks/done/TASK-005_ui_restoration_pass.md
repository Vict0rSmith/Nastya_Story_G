# TASK-005 — UI restoration pass

## Цель

Максимально привести существующий интерфейс Ren'Py к утвержденной `UI Design System v1` и композиционному направлению approved visual references **без создания новых графических ассетов**.

Это структурно-стилевой этап. Его задача — исправить геометрию, компоновку, панели, цвета, типографику, отступы, размеры, состояния, иерархию и повторно используемые компоненты средствами самого Ren'Py.

В рамках TASK запрещено производить новую художественную графику: PNG, JPG/WebP, SVG, иконки, предметные изображения, портреты, декоративные оболочки и другие новые image assets. Все, что невозможно корректно завершить без отдельной графики, фиксируется как `art-pool` для будущего отдельного TASK.

## Основание

Владелец проекта утвердил:

- `docs/systems/UI_VISUAL_SYSTEM_SPEC.md` как основной источник визуальных правил;
- четыре исходных макета как **approved visual references** для композиции и визуального направления;
- отказ от обязательного Figma-процесса;
- разделение UI restoration на два производственных слоя:
  1. текущий TASK — максимально возможная реализация средствами Ren'Py без генерации новых картинок;
  2. отдельный будущий TASK — производство и подключение недостающих графических ассетов.

Approved visual references не являются источником игровых данных и не требуют pixel-perfect копирования.

## Жесткая граница по графике

### Разрешено

- использовать встроенные возможности Ren'Py: `frame`, `button`, `imagebutton`, `textbutton`, `Solid`, `Frame`, `Transform`, `Alpha`, `Composite`, layout-контейнеры, стили, transforms и другие штатные средства движка;
- использовать цвет, прозрачность, рамки, padding, spacing, размеры, шрифтовые стили и состояния компонентов;
- переиспользовать уже существующие и уже закоммиченные runtime-ассеты проекта, если они подходят и не требуют создания новой картинки;
- использовать approved reference только как визуальный ориентир;
- оставлять аккуратные нейтральные программные placeholders там, где финальная графика еще отсутствует.

### Запрещено

- создавать новые PNG/JPG/WebP;
- создавать новые SVG;
- генерировать или рисовать новые иконки;
- создавать новые портреты, предметы, thumbnails одежды, фон коробки, фон шкафа, корпус телефона и другие raster/vector art assets;
- скачивать сторонние icon packs;
- встраивать внешнюю графическую библиотеку ради выполнения TASK;
- маскировать отсутствие художественного ассета случайным emoji или декоративным Unicode-символом.

Если компонент требует новой картинки, Codex **не блокирует весь TASK и не рисует ее**, а:

1. реализует максимально близкую структуру средствами Ren'Py;
2. оставляет нейтральный placeholder или существующий ассет;
3. добавляет конкретный пункт в `art-pool` implementation report.

## Что реализовать

### 1. Единый технический слой дизайн-системы

Привести `game/ui/design_system.rpy` и используемые им стили к `UI_VISUAL_SYSTEM_SPEC.md`.

Требования:

- повторяемые цвета идут через единые токены/стили;
- повторяемые размеры, padding, spacing и типографические параметры не дублируются хаотично;
- убрать локальные визуальные значения там, где существует общий токен;
- не создавать параллельную систему стилей;
- сохранить игровое поведение экранов;
- использовать только те эффекты и геометрию, которые реализуются средствами Ren'Py без новых art assets.

### 2. Functional UI без производства новых иконок

Текущий TASK **не создает семейство functional icons**.

Для элементов, которым в финальном UI потребуется отдельная пиктограмма:

- если подходящий существующий ассет уже есть — использовать его;
- если ассета нет — оформить элемент текстом, геометрией, цветом и состояниями Ren'Py так, чтобы он выглядел аккуратно и единообразно;
- не создавать новый SVG/PNG ради замены `Э`, `₽`, `◇`, `◆`, `✦`, `●`, `×` и аналогичных прототипных обозначений;
- по возможности убрать декоративные Unicode-заглушки, заменив их нормальной текстовой подписью или нейтральным программным элементом;
- все отсутствующие финальные иконки перечислить в `art-pool`.

Текстовый знак допустим только как функциональная временная надпись, а не как попытка выдать его за готовую художественную иконку.

### 3. HUD cleanup

Сохранить действующую структуру и игровую логику HUD, но максимально привести ее к дизайн-системе:

- Top Medallion — единая геометрия 68×68;
- World Tile — единая геометрия 104×104;
- выровнять интервалы, подписи, caption, selected/disabled/hover-состояния;
- нормализовать визуальный размер **существующих** HUD-ассетов средствами `Transform`, `xysize`, crop/fit и контейнеров, не перерисовывая сами картинки;
- устранить лишние локальные панели/отступы, которые можно исправить кодом;
- существующие PNG-состояния сохранить, если они уже используются;
- ресурсную панель оформить единообразно без создания новых пиктограмм;
- строка `Нормальное состояние` не должна изображать несуществующую динамическую систему эффектов;
- NPC actions привести к нормальной кнопочной/контекстной композиции без необходимости нового изображения.

Если несовместимая внутренняя рамка уже физически запечена в PNG и не может быть исправлена средствами Ren'Py без ухудшения — не редактировать изображение, а зафиксировать его замену в `art-pool`.

### 4. Карточка Насти

Восстановить композиционное направление `assets/ui/approved_references/nastya-card.png` средствами Ren'Py:

- заметная левая зона персонажа/preview;
- ресурсный блок;
- характеристики;
- информационная зона;
- навыки/доступная игроку системная информация;
- единые панели, заголовки, интервалы и визуальная иерархия.

При этом:

- не создавать новое изображение Насти;
- если подходящего runtime-портрета нет, оставить аккуратную зарезервированную область/placeholder;
- не копировать устаревший текст макета;
- убрать неверную захардкоженную строку про колледж и расписание `08:30–14:00`;
- меняющиеся данные по возможности брать из `game_state`;
- не придумывать отсутствующие факты.

### 5. Карточка Маши

- существующая кнопка Маши должна открывать карточку вместо `NullAction()`;
- карточка использует тот же структурный шаблон и Ren'Py-стили, что карточка Насти;
- не создавать новое изображение Маши;
- при отсутствии подходящего runtime-портрета использовать нейтральную зарезервированную область;
- отображать только канонические/доступные игроку сведения;
- не создавать новые показатели ради симметрии.

### 6. Телефон

Максимально приблизить экран к `assets/ui/approved_references/phone.png` **только средствами Ren'Py**:

- вытянутая смартфонная геометрия;
- выраженный внешний корпус/рамка из программных поверхностей;
- внутренний экран;
- status area;
- регулярная сетка приложений;
- единые размеры плиток;
- нижняя навигационная зона;
- системные отступы и визуальная иерархия;
- существующие приложения и действия сохраняются.

Не создавать новые иконки приложений, обои или графический корпус телефона. Там, где финальная иконка отсутствует, использовать аккуратную текстовую/геометрическую плитку и внести недостающую графику в `art-pool`.

Placeholder-приложения остаются честно недоступными; Camera/Gallery/Map/University не реализовываются механически ради внешнего вида.

### 7. Инвентарь

Максимально воспроизвести композицию `assets/ui/approved_references/inventory.png` средствами Ren'Py:

- общая форма/композиция «коробки» через панели, цветовые поверхности и layout;
- регулярная сетка;
- единые item cells;
- отдельная зона выбранного предмета;
- quantity badge;
- selected/hover/disabled-состояния;
- существующая логика использования предмета сохраняется.

Не создавать фон коробки и новые item images. Если item asset отсутствует, слот оформляется нейтрально текстом/пустым preview, а требуемое изображение фиксируется в `art-pool`.

### 8. Гардероб

Максимально воспроизвести композицию `assets/ui/approved_references/wardrobe.png` средствами Ren'Py:

- левая зона зеркала/персонажа;
- правая зона шкафа;
- визуальное разделение секций программными панелями;
- единая сетка одежды;
- категории не меняют геометрию окна;
- selected/equipped/disabled состояния;
- действующая equip/unequip-механика сохраняется.

Не создавать изображение шкафа, зеркало как raster art, изображение персонажа или thumbnails одежды. Отсутствующую графику фиксировать в `art-pool`.

### 9. Общие состояния и навигация

Для затронутых компонентов средствами Ren'Py обеспечить применимые:

- idle;
- hover;
- pressed;
- selected;
- disabled;
- focus.

Проверить длинные русские подписи, единые размеры кнопок, перенос текста и отсутствие скачков компоновки.

### 10. Cleanup

После перехода на общие программные компоненты:

- удалить реально неиспользуемые старые UI-стили только после проверки ссылок;
- не удалять существующий art asset только потому, что он визуально устарел — его замена относится к будущему графическому TASK;
- не оставлять две конкурирующие реализации одного восстановленного программного компонента;
- не изменять бинарные графические файлы в рамках TASK.

## Art-pool для следующего TASK

Implementation report TASK-005 обязан содержать отдельный раздел `Art-pool`.

В него включается каждый визуальный элемент, который не удалось довести до финального вида без нового графического ассета. Для каждого пункта указать:

- экран/компонент;
- что именно отсутствует или требует замены;
- предполагаемый класс ассета: functional icon / app icon / item image / wardrobe thumbnail / character preview / decorative shell / HUD asset;
- рекомендуемый размер/safe area, если он уже однозначно следует из дизайн-системы;
- приоритет: critical / normal / optional.

Этот список станет входом для отдельного будущего TASK по графическим ассетам. TASK-005 не должен сам выполнять элементы `art-pool`.
