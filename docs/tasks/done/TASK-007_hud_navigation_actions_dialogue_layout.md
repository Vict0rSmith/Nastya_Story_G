# TASK-007 — HUD navigation/actions cleanup and dialogue-mode layout

## Цель

Переработать основной игровой HUD так, чтобы свободное управление и режим чтения сцены визуально и функционально были разделены, а все повторяющиеся HUD-плитки имели аккуратную и предсказуемую геометрию.

Итоговый результат:

- нижний левый ряд показывает только доступные переходы;
- нижний правый ряд показывает только доступные действия;
- подписи обеих групп короткие и симметричные;
- подпись каждой плитки визуально центрирована относительно своей кнопки/медальона;
- полные названия и длительность/время перехода показываются только при hover/focus;
- во время диалога или авторского текста нижняя управляющая зона полностью заменяется полноширинным dialogue UI с текстом и доступным портретом/аватаром говорящего;
- системные всплывающие сообщения выводятся по центру под верхней центральной группой, не перекрывая панели HUD;
- верхняя правая панель времени/даты/локации имеет компактную высоту и не конфликтует с блоком присутствующих NPC (`ЗДЕСЬ`, Маша и т. п.).

## Основание

Владелец проекта 2026-09-07 утвердил следующие изменения базового HUD:

1. Не показывать текущую локацию отдельной плиткой в нижнем ряду переходов: она уже постоянно отображается в верхней правой группе HUD.
2. На плитках переходов использовать лаконичное HUD-название; полное естественное название и время перехода показывать только при hover/focus.
3. Не добавлять в полные UI-названия очевидный контекст вроде `Кухня квартиры №5`, если игроку достаточно `Кухня`.
4. Симметрично применить тот же принцип к действиям: короткая подпись на плитке, полное название и длительность только при hover/focus.
5. Убрать постоянно видимые строки времени/длительности из нижних плиток переходов и действий.
6. Во время диалога/авторского текста нижние переходы и действия не должны оставаться активными или визуально конкурировать с текстом. Dialogue UI заменяет нижнюю управляющую зону целиком.
7. Системные `notify`/всплывающие сообщения переместить из верхней левой области под верхнюю центральную группу кнопок.
8. Все подписи под HUD-кнопками должны быть геометрически центрированы относительно соответствующей кнопки/медальона. Недопустимы случайные смещения влево/вправо или разный принцип выравнивания у соседних плиток.
9. Верхняя правая панель времени/даты/локации сейчас визуально конфликтует с расположенным ниже блоком присутствующих NPC. Панель следует сделать компактнее по высоте и/или скорректировать ее вертикальную геометрию так, чтобы она не перекрывала `ЗДЕСЬ` и первый NPC. При этом содержимое панели должно оставаться полностью читаемым.

Текущая `docs/systems/UI_VISUAL_SYSTEM_SPEC.md` содержит более старые правила (`текущая локация показывается первой`, постоянная дополнительная строка/время). Поэтому **до изменения runtime-кода Codex обязан синхронизировать UI-спецификацию с утвержденными решениями владельца**, включая новые требования по центрированию подписей и отсутствию перекрытия верхней правой панели с NPC-блоком.

## Что реализовать

### 1. Сначала синхронизировать UI Design System

Обновить `docs/systems/UI_VISUAL_SYSTEM_SPEC.md` только в пределах реально затронутых правил HUD:

- в `9.4 Нижние переходы` убрать требование показывать текущую локацию первой;
- закрепить, что нижняя группа содержит только доступные цели перехода;
- закрепить короткое HUD-название на плитке и hover-detail с полным естественным названием + временем перехода;
- убрать требование постоянно показывать время пути под плиткой;
- в `9.5 Нижние действия` закрепить симметричный паттерн: короткое HUD-название на плитке, hover-detail с полным названием + длительностью; постоянную строку длительности убрать;
- для World Tile/Top Medallion закрепить единый принцип: подпись центрируется относительно геометрии плитки/медальона, а не относительно собственной ширины текста или случайного layout-контейнера;
- для многострочных подписей закрепить центральное `text_align` и одинаковую доступную ширину подписи внутри плитки;
- добавить правило режима нижней зоны: `free-roam controls` и `dialogue/scene` взаимоисключающие;
- добавить правило размещения системных уведомлений под верхней центральной группой, по центру экрана;
- закрепить, что верхняя правая информационная панель должна оставаться компактной и иметь гарантированный визуальный зазор до блока присутствующих NPC;
- не менять другие разделы дизайн-системы без прямой необходимости.

После синхронизации документа код реализуется именно по обновленной спецификации.

### 2. Нижние переходы

Текущую плитку `ВЫ ЗДЕСЬ` удалить из нижней группы.

Нижняя левая группа должна содержать только реальные доступные переходы из текущей локации.

Требования:

- сохранять геометрию World Tile из дизайн-системы;
- использовать короткую подпись, пригодную для HUD;
- не выводить `N мин.` отдельной постоянной строкой;
- hover/focus показывает компактную строку вида `Кухня · 1 мин.`;
- не использовать служебные/избыточные формулировки вроде `Переход:`;
- полное hover-название должно быть естественным для игрока и не дублировать очевидную иерархию пространства (`Кухня`, а не `Кухня квартиры №5`, если дополнительная квалификация не нужна для различения локаций);
- при отсутствии отдельного короткого имени должен существовать безопасный fallback на обычное имя без поломки UI.

### 3. Короткие и полные имена локаций

Не переименовывать стабильные ID и не урезать обычное имя сущности только ради HUD.

Реализовать отдельное представление короткой подписи для HUD (`short_name`, UI helper/map или эквивалентное решение, совместимое с текущей моделью данных).

Контракт:

- обычное имя сущности остается источником полного UI-названия;
- короткое имя используется только в компактной HUD-плитке;
- если короткое имя не задано, используется обычное имя;
- не создавать второй источник топологии и не менять `map.drawio`;
- не размазывать сокращения по screen-коду.

Если отдельное поле в данных создает лишний риск для save compatibility, использовать централизованный UI metadata/helper.

### 4. Нижние действия

Применить тот же визуальный контракт, что к переходам:

- на плитке — короткое HUD-название;
- постоянную строку `N мин.` убрать;
- при hover/focus — полное естественное название + длительность, например `Принять душ · 15 мин.`;
- не добавлять слова `Действие:` / `Время:` без функциональной необходимости;
- если действие заблокировано, причина блокировки должна оставаться доступной игроку через единый hover/tooltip-паттерн;
- существующие duration/energy/cooldown/availability rules не менять.

Короткие имена действий централизовать тем же принципом, что короткие имена локаций.

### 5. Геометрия и центрирование подписей HUD

Провести отдельный cleanup выравнивания подписей у повторяющихся HUD-плиток, прежде всего нижних переходов и действий, а также затронутых верхних медальонов/NPC tiles, если они используют тот же компонент или страдают от той же проблемы.

Требования:

- иконка/медальон и подпись должны иметь общий фиксированный контейнер плитки;
- горизонтальный центр текста должен совпадать с горизонтальным центром кнопки/медальона;
- использовать явное центрирование контейнера и текста (`xalign`/`text_align`/фиксированная ширина или эквивалент), а не полагаться на неочевидное наследование свойств `vbox`;
- все соседние плитки одного семейства используют одинаковую ширину подписи;
- однословные, длинные и многострочные русские подписи остаются визуально центрированными;
- перенос строки не должен сдвигать визуальный центр плитки;
- не уменьшать шрифт ниже дизайн-системы только ради вмещения текста;
- проверить idle/hover/selected/disabled/focus: смена состояния не должна двигать подпись относительно кнопки;
- после переработки не должно быть плиток, где подпись визуально «прилипла» к левому/правому краю или центрируется относительно собственной ширины вместо кнопки.

Цель — единый предсказуемый паттерн, а не ручные `xoffset` для отдельных строк.

### 6. Единый hover-detail для переходов и действий

Сделать один визуально согласованный компактный hover/tooltip-компонент либо два компонента на общей основе.

Требования:

- появляется только при наведении/фокусе;
- располагается над нижним рядом и не закрывает соседние кнопки;
- переход: `Полное название · N мин.`;
- действие: `Полное название · N мин.`;
- для disabled action дополнительно показать причину недоступности в той же системе;
- не превращать hover в справочное окно и не повторять очевидную информацию.

### 7. Нижняя зона в режиме диалога/сцены

Переработать `say`-композицию и взаимодействие с gameplay HUD.

Во время показа реплики персонажа или авторского текста:

- нижние переходы и действия **не рендерятся как интерактивные элементы**;
- под dialogue panel не должно оставаться кликабельных/focusable controls;
- нижнюю игровую зону занимает полноширинная dialogue panel с разумными боковыми полями в рамках базового 1920×1080;
- dialogue panel визуально центрирована по ширине;
- панель размещается у нижнего края и использует освобожденную высоту нижнего HUD;
- если `who is not None`, показывать имя говорящего и существующий доступный avatar/SideImage/portrait в рамках новой композиции;
- если это авторский текст (`who is None`), не оставлять пустой декоративный слот под аватар; текст использует доступную ширину;
- не создавать новые художественные портреты/аватары в этом TASK;
- если подходящего runtime-аватара нет, использовать корректный текстовый dialogue layout без выдуманной картинки.

Архитектурный принцип:

`FREE_ROAM = transitions + actions`

`DIALOGUE_SCENE = dialogue panel (+ speaker avatar if available)`

После завершения реплики/сцены свободный HUD возвращается штатно.

Не менять содержание реплик, авторского текста, character voice или сценарные ветки.

### 8. Системные всплывающие сообщения

Переработать `screen notify(message)` / соответствующий стиль:

- убрать позиционирование в верхней левой области;
- размещать уведомление горизонтально по центру экрана;
- вертикально — под верхней центральной группой Top Medallion;
- сообщение не должно перекрывать верхнюю левую ресурсную панель, верхнюю правую панель времени/локации и центральные кнопки;
- ширина определяется содержимым с разумным максимальным ограничением;
- длинное сообщение допускает перенос, но notify остается компактным;
- сохранить существующую анимацию появления/исчезновения, если она не мешает новой позиции.

### 9. Верхняя правая информационная панель и NPC-блок

Проверить текущую верхнюю правую композицию в `game_hud`.

Фактическая текущая реализация задает панели времени/дня/локации примерно:

- `xpos 1636`;
- `ypos 24`;
- `xsize 260`;
- `ysize 104`;

а блок присутствующих NPC начинается ниже (`ypos 155`) с подписи `ЗДЕСЬ`.

В стартовой комнате, когда Маша находится в той же локации, владелец визуально наблюдает наложение/наезд верхней правой панели на область `ЗДЕСЬ`/Маша.

Требования:

- проверить этот сценарий именно в runtime/preview, а не только по арифметике координат;
- уменьшить избыточную высоту верхней правой панели, если содержимое реально помещается в более компактный контейнер;
- предпочтительно сохранить верхнюю привязку панели (`y≈24`) и уменьшить ее вниз, а не просто сдвинуть весь блок ниже;
- допускается небольшая корректировка вертикальных отступов/spacing/типографики внутри панели, если это не ухудшает читаемость;
- обеспечить явный визуальный зазор между нижней границей панели и `ЗДЕСЬ`/первым NPC;
- не допускать перекрытия фона панели, текста, hover/focus-эффектов или NPC-элементов;
- не убирать из панели время, день недели, текущую локацию или период дня ради уменьшения высоты;
- не увеличивать панель обратно из-за случайных внутренних padding, если их можно привести к дизайн-системе;
- если фактическая причина перекрытия находится не в `ysize`, а в padding/style/background или позиционировании NPC-блока, исправить первопричину минимально и системно.

### 10. Текущая локация

Текущая локация продолжает отображаться в верхней правой группе HUD рядом со временем/периодом дня.

Не добавлять второй постоянный индикатор текущей локации снизу.

Если после удаления нижней selected-плитки верхняя индикация визуально теряется, допускается минимальная корректировка типографики/акцента в пределах дизайн-системы.

## Данные и сущности

Разрешается минимально расширить runtime-модель представления локации/действия коротким HUD-названием, если это соответствует фактической архитектуре.

Нельзя:

- менять стабильные ID локаций или действий;
- менять топологию;
- менять длительность переходов;
- менять длительность/стоимость/условия действий;
- менять save semantics без реальной необходимости.

Если добавление поля в сериализуемый объект затрагивает save compatibility, предпочесть несериализуемый definition/UI metadata слой либо обеспечить безопасный migration/default.

## UI / UX

Общий принцип HUD после TASK:

- свободная игра: `переходы слева ← свободный центр → действия справа`;
- нижние плитки: иконка + короткая подпись, строго центрированная относительно плитки;
- подробности появляются по hover/focus;
- диалог/сцена временно заменяет всю нижнюю управляющую область;
- system notify живет отдельно под верхней центральной группой;
- верхняя правая информационная панель не конкурирует с вертикальным NPC-блоком.

Сохранять центральную игровую сцену максимально свободной в соответствии с UI Design System.

## Контент

TASK не создает и не редактирует художественный игровой текст. Существующие реплики/авторский текст должны отображаться в новом layout без содержательной редакции.

Если для проверки потребуется тестовая строка, использовать технический тестовый контент вне канонических сцен либо существующий контент без изменения его текста.

## Интеграции с существующими системами

- `LOCATIONS` и runtime transitions — только чтение существующих маршрутов; топология не меняется.
- `ACTIONS` / `ActionDefinition` — существующие правила выполнения сохраняются.
- `game_hud` — нижние группы и верхняя правая композиция перерабатываются без изменения механики movement/action execution.
- `say` / `SideImage` — перестраивается только UI-композиция.
- `notify` — меняется только позиционирование/компоновка, а не семантика вызовов `renpy.notify`.
- keyboard focus/gamepad navigation должны учитывать исчезновение free-roam controls во время dialogue mode.

## Не делать

- не менять `docs/graphs/map.drawio`;
- не менять состав или направление переходов;
- не менять игровые значения времени/энергии/стоимости;
- не создавать новые PNG/SVG/портреты/аватары;
- не редактировать текст сцен и диалогов;
- не делать отдельную большую tooltip-систему для всего проекта за пределами нужд World Tile;
- не добавлять мобильный redesign, если текущие изменения не требуют минимальной совместимости существующего variant;
- не рефакторить несвязанные модальные экраны, телефон, инвентарь, гардероб или карточки персонажей;
- не использовать индивидуальные pixel-offset хаки для каждой подписи вместо единой геометрии компонента;
- не сохранять старый и новый нижний HUD как две конкурирующие реализации.

## Критерии приемки

1. В нижнем левом ряду нет плитки текущей локации и подписи `ВЫ ЗДЕСЬ`.
2. Верхняя правая группа по-прежнему показывает текущую локацию.
3. Переходы показывают короткое имя на плитке и не показывают время постоянно.
4. Hover/focus перехода показывает полное естественное название + длительность перехода.
5. Действия показывают короткое имя на плитке и не показывают длительность постоянно.
6. Hover/focus действия показывает полное название + длительность; disabled action сохраняет доступную причину блокировки.
7. Короткие имена централизованы и имеют fallback, стабильные ID не меняются.
8. Все подписи под transition/action World Tile визуально центрированы относительно соответствующих медальонов; однословные и многострочные подписи используют одинаковый принцип.
9. Затронутые Top Medallion/NPC tiles не имеют очевидных разъездов центрирования, если используют общий компонент.
10. Смена hover/selected/disabled/focus не сдвигает подписи.
11. Во время `say`/авторского текста нижние transitions/actions не рендерятся и не доступны кликом/focus.

## Примечания для исполнителя

Перед началом использовать `origin/main` как источник актуального состояния, прочитать Board и Context Manifest, затем проверить текущую реализацию до изменения.

TASK содержит утвержденные владельцем изменения UI, которые частично расходятся с прежней редакцией `UI_VISUAL_SYSTEM_SPEC.md`. Это не блокер: прямое актуальное решение владельца имеет приоритет. Сначала синхронизировать основной UI-источник, затем реализовывать код по уже обновленной спецификации.

Если фактическая архитектура требует выбрать между отдельным `short_name` в definition-данных и централизованным UI metadata/helper, выбрать вариант с меньшим риском для save compatibility и без дублирования строк по screen-коду.

При выравнивании подписей не использовать индивидуальные offsets как основной способ решения: исправить общий layout-контракт плитки.

При исправлении верхней правой панели сначала определить фактическую причину наложения в runtime (жесткая высота, padding/style/background либо NPC position), затем исправить минимально и системно.

При обнаружении реального противоречия, требующего нового продуктового решения, не угадывать — вынести владельцу.
