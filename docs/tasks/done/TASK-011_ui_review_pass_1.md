# TASK-011 — UI review pass 1: HUD, actions, phone and system menus

## Цель

Провести первый целевой визуальный и UX-проход по текущему интерфейсу и устранить утвержденный владельцем пакет замечаний к HUD, действиям, экрану заданий и календаря телефона, а также системным меню Ren'Py.

Итог должен:

- убрать дублирующие и зависающие уведомления;
- убрать лишние подтверждающие клики у однозначных действий;
- улучшить композицию верхних HUD-блоков;
- привести действия с персонажами к компактному строчному формату;
- сделать checklist задания компактным единым блоком;
- сделать карточку календарного события устойчивой и убрать ненужный scrollbar;
- убрать негармоничные коричневые/грязно-коричневые поверхности из затронутого UI и синхронизировать палитру через Design System;
- полностью привести системные menu screens к цельному фону и русскому пользовательскому интерфейсу;
- убрать видимые игроку ошибки отсутствующих GUI-ассетов и другие технические артефакты.

Это один связный UI-review pass. Не дробить его на девять независимых локальных фиксов, если одна и та же компонентная или стилeвая причина затрагивает несколько экранов.

## Основание

Владелец проекта 2026-09-15 провел визуальную приемку текущей реализации и утвердил девять групп изменений по скриншотам.

Часть решений уточняет или меняет действующие правила `UI_VISUAL_SYSTEM_SPEC.md`. Поэтому **до изменения runtime-кода Codex обязан синхронизировать только реально затронутые правила UI Design System с решениями ниже**, после чего реализовать код уже по обновленной спецификации.

Скриншоты были даны владельцем как визуальная иллюстрация замечаний. Настоящий TASK содержит самодостаточные требования и является рабочей формализацией этого review.

## Что реализовать

### 1. Системные notify: не дублировать текущую локацию

Текущее всплывающее сообщение вида `Общая комната` после входа в комнату не нужно: текущая локация уже постоянно отображается в верхнем правом HUD.

Требования:

- убрать `notify`/аналогичные всплывающие сообщения о простом перемещении между комнатами и локациями, если они лишь повторяют уже видимую текущую локацию;
- не удалять сам системный компонент уведомлений;
- использовать его для действительно новой полезной информации: получение/обновление задания, получение предмета, появление/изменение статуса, важное системное событие и аналогичные случаи;
- проверить все прямые вызовы `renpy.notify`/эквивалента, связанные с навигацией, и убрать только дублирующие location-entry сообщения;
- временное уведомление должно гарантированно исчезать по завершении своего времени показа и не зависать на экране;
- не превращать уведомление в постоянный второй индикатор локации.

Каноническое UX-правило: временное уведомление сообщает **новое состояние или событие**, а не повторяет постоянно видимую информацию HUD.

### 2. Однозначное действие выполняется одним нажатием

Сейчас при выборе действия `Подождать час` игрок дополнительно получает промежуточную панель и должен еще раз нажать `Выполнить`. Для однозначного действия это лишний шаг.

Требования:

- `Подождать час` должно выполняться непосредственно по нажатию на его кнопку/плитку;
- применить это правило ко всем обычным детерминированным одношаговым gameplay actions того же класса: если выбор действия уже однозначно определяет результат, второй клик `Выполнить` не требуется;
- вторичный экран/меню сохранять только там, где после выбора действия действительно нужен дополнительный выбор: несколько вариантов, параметр действия, выбор цели/предмета, либо осознанное подтверждение действительно особого необратимого действия;
- не менять стоимость энергии, длительность, cooldown, availability или последствия самих действий без отдельного требования;
- hover/focus-detail и причины недоступности должны сохраниться.

Общее правило UX:

```text
single deterministic action -> immediate execution
multi-option / parameterized action -> secondary choice UI
```

### 3. Перенести статусы вправо от ресурсов

В верхнем левом HUD статусы сейчас располагаются под панелью `Деньги / Энергия`.

Требования:

- перенести статусную группу вправо от панели ресурсов;
- выровнять ее по общей верхней композиции ресурсного блока;
- не оставлять под ресурсной панелью случайный второй вертикальный столбец, если для него нет отдельной необходимости;
- сохранить доступность всех существующих статусов и их семантику;
- если несколько типов статусов используют общий компонент, исправлять компонентно, а не отдельными `xoffset` для конкретного статуса.

### 4. Действия с присутствующим персонажем — строчный список

Текущая панель действий с персонажем использует крупные круглые медальоны по аналогии с нижним рядом gameplay actions. Для контекстного списка действий NPC этот формат больше не использовать.

Требования:

- панель `ДЕЙСТВИЯ: <ПЕРСОНАЖ>` должна отображать действия компактными строками;
- визуальный принцип — как у checklist: маленький тематический значок/маркер слева и текст действия справа;
- чекбокс как семантика выполнения не нужен, если действие не является checklist-item; использовать подходящую маленькую functional/subject icon;
- строки должны находиться в едином компактном контейнере, иметь единые отступы и понятные hover/disabled состояния;
- крупные круглые action-medallions внутри NPC action panel удалить;
- не менять сами доступные действия, условия и последствия.

### 5. Перекомпоновать верхний правый информационный блок

Вся текущая информация нужна: время, текущая локация, день недели и время суток. Проблема только в композиции.

Требования:

- собрать информацию в компактную и визуально устойчивую структуру;
- рекомендуемая базовая иерархия: первая строка — крупное время слева и день недели справа; вторая строка — текущая локация слева и время суток справа;
- допустима эквивалентная композиция, если она выглядит лучше в реальном runtime и сохраняет ту же ясную иерархию;
- значения не должны выглядеть случайно разбросанными по углам панели;
- сохранить читаемость русских длинных названий локаций;
- сохранить гарантированный зазор до блока присутствующих NPC ниже.

### 6. Экран задания: один checklist вместо отдельных карточек каждой цели

На карточке задания `Первый нормальный день` каждая подзадача сейчас находится в отдельной крупной фиолетовой карточке, из-за чего единый checklist визуально распадается и занимает лишнюю высоту.

Требования:

- заголовок/описание самого задания можно оставить отдельным верхним блоком;
- все подзадачи одного задания разместить внутри **одного общего checklist-контейнера**;
- каждая подзадача — компактная строка: checkbox + текст;
- между строками использовать умеренный вертикальный интервал и при необходимости тонкий разделитель, но не отдельную большую фиолетовую карточку на каждый пункт;
- выполненные/невыполненные состояния должны оставаться различимыми;
- длинные русские строки должны корректно переноситься без разрыва общей геометрии списка;
- не менять структуру квеста, количество целей и quest runtime.

### 7. Календарь: устойчивое выбранное событие и scrollbar только по необходимости

При наведении на дату с событием информационная карточка сейчас пропадает сразу после ухода курсора с даты. Это неудобно для чтения.

Требования:

- hover/focus на дате с событием должен обновлять `selected event day`/эквивалентное устойчивое UI-состояние;
- карточка события остается видимой после ухода курсора с выбранной даты;
- она меняется, когда игрок наводит/фокусирует другую дату, на которой есть другое событие;
- наведение на обычный день без события не должно само по себе очищать последнюю выбранную карточку;
- mouse и keyboard/focus поведение должны быть согласованы;
- если событий/текста столько, что они полностью помещаются в карточку, вертикальный scrollbar не показывать;
- scrollbar появляется только при реальном overflow;
- при одном событии `День рождения: Маша` scrollbar отсутствует;
- существующие календарные данные и даты не менять.

Предпочтительная реализация — устойчивое selected-state, а не попытка искусственно удерживать hover.

### 8. Убрать коричневые/грязно-коричневые UI-поверхности из затронутой системы

Владелец отверг текущие выраженные коричневые/грязно-коричневые поверхности, видимые в календаре, системных меню и связанных подложках.

Требования:

- пересмотреть затронутые neutral/HUD/menu surface tokens в `UI_VISUAL_SYSTEM_SPEC.md`;
- подобрать более гармоничную нейтральную палитру, совместимую с текущими teal/violet/coral/amber акцентами и телефонной графикой;
- не заменять коричневые поверхности случайными inline-цветами в отдельных screens;
- повторяемые цвета оформить централизованными семантическими токенами/стилями;
- убрать визуально грязные umber/brown панели, полосы и empty-slot подложки в пределах затронутых экранов;
- сохранить достаточный контраст текста, hover, selected, disabled и borders;
- не менять игровые semantic accent colors без необходимости.

Это утвержденное изменение направления палитры, поэтому Design System и реализация должны быть синхронизированы в одном TASK.

### 9. Save/Load — цельный полноэкранный системный экран

Текущие экраны сохранения и загрузки содержат разорванный фон, вертикальную полосу/подложку и несогласованные коричневые области.

Требования:

- фон системного menu screen должен быть цельным на весь экран 1920x1080, без случайно оставшихся областей старой темы;
- убрать вертикальную полосу/подложку, визуально пересекающую левую навигацию и контент;
- привести область слотов сохранения к единой новой нейтральной палитре;
- empty slot не должен выглядеть как случайный сплошной коричневый прямоугольник;
- проверить selected/hover/current page states;
- сохранить функциональность сохранения и загрузки;
- не ломать существующие screenshot thumbnails и slot metadata.

### 10. Полная пользовательская русификация системных меню

По скриншотам в UI остаются `Save`, `Load`, `Page 1`, `Return`, `empty slot`, `Yes`, `No`, а также английские элементы quick menu и английское форматирование части пользовательских данных.

Требования:

- перепроверить все стандартные пользовательские menu screens Ren'Py, а не только Save/Load/Quit;
- как минимум проверить: `История`, `Сохранить`, `Загрузить`, `Настройки`, `Главное меню`, `Об игре`, `Помощь`, `Выход`, confirm dialogs и видимый quick menu;
- все player-facing labels должны быть по-русски, если отдельный английский термин не утвержден владельцем;
- локализовать page labels, back/return, empty slot, yes/no и другие стандартные подписи;
- проверить quick menu (`Back`, `History`, `Skip`, `Auto`, `Save`, `Q.Save`, `Q.Load`, `Prefs`) и либо корректно русифицировать его, либо привести к утвержденному русскому эквиваленту интерфейса;
- не оставлять смешанный русско-английский UI на одном экране;
- если дата/день недели в метаданных сохранений выводятся английской локалью, привести player-facing форматирование к русскому представлению без изменения самих timestamp-данных.

### 11. Экран выхода: убрать raw error отсутствующего `confirm_frame.png`

На экране выхода сейчас виден технический текст вида `Couldn't find file 'gui/confirm_frame.png'` поверх confirm dialog.

Требования:

- найти причину обращения к отсутствующему `gui/confirm_frame.png`;
- либо восстановить корректный asset, если он действительно является частью утвержденной UI-системы, либо убрать устаревшую зависимость и собрать confirm frame средствами актуальных styles/components;
- player-facing экран никогда не должен показывать raw missing-file error;
- confirm dialog полностью русифицировать;
- фон и палитру привести к тем же правилам системных меню;
- проверить не только `Quit`, но все места, где используется общий `confirm` screen.

### 12. Общая ревизия связанных menu screens

После локальных исправлений сделать визуальную ревизию всего семейства стандартных menu screens, чтобы не оставить тот же дефект на соседнем экране.

Проверить как минимум:

- main menu;
- game menu/navigation;
- history;
- save;
- load;
- preferences/settings;
- about;
- help;
- quit/confirm;
- quick menu в gameplay, если он рендерится;
- общие shared styles/backgrounds, которыми пользуются перечисленные screens.

Исправлять только дефекты, происходящие от тех же утвержденных правил палитры, локализации, фона и общих компонентов. Не придумывать новый дизайн для несвязанных систем.

## Данные и сущности

Игровые данные, канонические даты, квестовые цели, стоимость/длительность действий и сами статусы в рамках TASK не меняются.

Особенно:

- не менять дату рождения Маши и другие календарные даты;
- не менять состав целей `Первого нормального дня`;
- не менять energy/time/cooldown values;
- не переименовывать stable IDs;
- не менять world topology.

## UI / UX

### Сначала синхронизировать Design System

Перед runtime-правками обновить `docs/systems/UI_VISUAL_SYSTEM_SPEC.md` только в пределах решений этого TASK:

1. notify не используется для дублирования текущей локации;
2. детерминированное одношаговое действие выполняется одним нажатием;
3. статусы располагаются справа от resource panel;
4. NPC actions используют compact row list, а не medallion tiles;
5. top-right info panel использует цельную двухуровневую/эквивалентную композицию;
6. quest objectives внутри одной карточки образуют единый checklist block;
7. calendar event detail имеет устойчивое selected-state и conditional scrollbar;
8. neutral/menu surfaces пересматриваются без выраженной коричневой/umber доминанты;
9. системные menu screens имеют цельный фон и русский player-facing UI;
10. missing asset/error text не допускается как часть пользовательского интерфейса.

Не переписывать незатронутые разделы дизайн-системы.

### Компонентный принцип

Если один дефект повторяется на нескольких screens, исправлять общий style/component/token, а не копировать локальный фикс.

Не использовать набор ручных `xoffset/yoffset` для маскировки системной layout-проблемы.

## Контент

TASK не создает и не редактирует литературный игровой текст. Writing Pipeline для художественного контента не требуется.

Допустима только UI-локализация стандартных системных строк и коротких технических label/tooltip, необходимых для выполнения TASK.

## Интеграции с существующими системами

Сохранить существующие контракты:

- gameplay HUD и navigation/action runtime;
- quest runtime;
- phone data adapters;
- calendar event data;
- statuses/effects;
- Ren'Py save/load API;
- стандартные rollback/save compatibility ограничения проекта.

TASK меняет представление и UX-путь, а не смысл игровых механик.

## Не делать

- не менять топологию мира или `map.drawio`;
- не менять баланс, длительность, энергию, cooldown и последствия действий;
- не менять квестовые факты и состав целей;
- не менять даты персонажей/праздников;
- не вводить новые приложения телефона;
- не перерабатывать содержательно контакты/сообщения/банк/университетское приложение, если это не требуется прямой общей UI-зависимостью;
- не переписывать весь `screens.rpy` без необходимости;
- не добавлять второй набор palette constants параллельно Design System;
- не оставлять английский текст как временную заглушку;
- не объявлять визуальную проверку выполненной без реального runtime просмотра.

## Критерии приемки

TASK считается готовым к `review`, когда выполнены все условия ниже.

### HUD и действия

- [ ] при обычном переходе в `Общую комнату` и другие комнаты не появляется дублирующий location notify;
- [ ] значимые системные notify продолжают работать;
- [ ] notify автоматически исчезает и не остается висеть;
- [ ] `Подождать час` выполняется одним нажатием;
- [ ] другие обычные одношаговые deterministic actions того же класса не требуют бессмысленного второго `Выполнить`;
- [ ] multi-option actions сохраняют реальный дополнительный выбор;
- [ ] статусы находятся справа от resource panel;
- [ ] NPC action panel отображает compact rows с маленькой иконкой и текстом;
- [ ] time/location/weekday/daypart panel выглядит цельно и не конфликтует с NPC block.

### Телефон

- [ ] objectives одного quest отображаются единым checklist block;
- [ ] отдельные большие purple cards на каждую objective отсутствуют;
- [ ] выбранное calendar event остается после ухода курсора с даты;
- [ ] другое event-date обновляет карточку;
- [ ] non-event hover не очищает последнюю выбранную карточку;
- [ ] при одном коротком событии scrollbar отсутствует;
- [ ] при реальном overflow scrolling остается доступным.

### Палитра и системные меню

- [ ] выраженные коричневые/umber surfaces в затронутых экранах заменены согласованной нейтральной палитрой через централизованные tokens/styles;
- [ ] Save/Load имеют цельный фон без вертикальной полосы и старых подложек;
- [ ] empty slots не выглядят как случайные коричневые блоки;
