# TASK-008 — Унифицированные предметы, гардероб, интимные предметы и HUD состояний

## Цель

Привести систему предметов, одежды, интимных предметов и связанных с ними состояний к единой архитектуре без дублирования сущностей.

В результате TASK должны быть:

1. отдельная унифицированная карточка `item`;
2. четкое разделение `object` и `item`;
3. единый инвентарь с интерфейсными категориями;
4. отдельная вкладка инвентаря `Интимное`;
5. единый гардероб без отдельных домашних/рабочих копий;
6. контекстная доступность одной и той же одежды в разных сценариях;
7. поддержка предметов-действий;
8. поддержка предметов, которые могут длительно оставаться установленными на теле;
9. интеграция таких предметов с событиями;
10. компактная панель критических/пиковых состояний персонажа;
11. 20 утвержденных товарных карточек секс-шопа.

Основной архитектурный принцип:

> **Одна физическая сущность должна иметь одно определение. Владение, текущее место, допустимость использования, сюжетный доступ и временное состояние являются отдельными слоями и не создают копий предмета.**

## Основание

Текущая система уже содержит единый inventory, отдельный wardrobe, технические слоты одежды, характеристики энергии/настроения/возбуждения и HUD временных эффектов. При этом действующая модель недостаточно универсальна для одной вещи, используемой в разных сценариях, личной вещи Насти, позже разрешенной как рабочая одежда, предметов, которые остаются установленными на теле между действиями, и отдельной интерфейсной категории интимных предметов.

Текущая wardrobe-спецификация уже закрепляет принцип одного определения вещи и отсутствие дублирующих технических слотов по контекстам, но рабочая одежда далее описана через отдельный workplace wardrobe. Этот участок нужно синхронизировать с утвержденной моделью единого гардероба.

## Что реализовать

### 1. Развести `object` и `item`

Зафиксировать системное различие.

**Object** — устойчивый объект игрового мира. Он существует в пространстве, может осматриваться, иметь состояние, предоставлять действия и участвовать в нескольких сценах. Для него сохраняется `docs/templates/OBJECT_TEMPLATE.md`.

**Item** — переносимая или принадлежащая персонажу физическая вещь. Она может покупаться, храниться, переноситься, надеваться, использоваться, расходоваться, участвовать в действиях и временно переходить в другое физическое состояние.

Не создавать одновременно `object` и `item` только потому, что один и тот же товар виден в магазине, комнате или событии.

### 2. Создать `docs/templates/ITEM_TEMPLATE.md`

Минимальный front matter:

```yaml
---
id: item_example
entity_type: item
status: draft

name: Название предмета

category: misc
storage: inventory
item_type: misc

stackable: false
consumable: false
usable: true

required_openness_purchase: null
required_openness_use: null

price: TBD

tags: []
icon: null

use_modes: []

related_actions: []
related_effects: []
related_quests: []
related_events: []
---
```

Технические имена полей допускается скорректировать при реализации под существующий naming convention, но семантика обязательна.

Карточка должна позволять описать:

- стабильный `id`;
- отображаемое название;
- тип и категорию;
- обычное место хранения;
- `stackable`;
- `consumable`;
- `usable`;
- требование к покупке;
- требование к использованию;
- цену;
- теги;
- графический asset;
- способы использования;
- связанные actions/effects/events/quests.

Для одежды дополнительно должна поддерживаться связь с гардеробом и слотами. Для persistent body item должна поддерживаться возможность длительного состояния на теле.

Минимальный читаемый формат:

```md
# Название

## Что это

## Категория

## Хранение

## Внешний вид

## Игровое описание

## Покупка

## Использование

## Способы использования

## Условия доступности

## Состояния

## Графический ассет

## Связанный контент
```

Неприменимые разделы можно опускать.

### 3. Создать каноническое место item-карточек

Если в актуальном репозитории нет уже существующего более подходящего каталога, создать:

```text
docs/world/items/
    README.md
    ...item cards...
```

`README.md` должен быть картой карточек и не дублировать общую механику inventory/wardrobe.

Если при проверке найден существующий канонический item-каталог, расширить его вместо создания параллельного.

### 4. Синхронизировать навигацию и шаблоны

Обновить `docs/templates/README.md` и реально затронутые тематические MOC/README так, чтобы было понятно:

- когда используется `OBJECT_TEMPLATE.md`;
- когда используется `ITEM_TEMPLATE.md`;
- где находятся item-карточки.

## Данные и сущности

### 5. Единый inventory

Сохраняется один игровой inventory.

Не создавать:

- `sex_shop_inventory`;
- отдельный «интимный склад»;
- отдельный inventory секс-игрушек.

Интерфейсные категории являются фильтрами одного inventory.

### 6. Вкладка `Интимное`

В UI inventory должна существовать отдельная вкладка/фильтр `Интимное`.

В нее входят:

- секс-игрушки;
- лубрикант;
- презервативы;
- порножурнал;
- порнофильм;
- иллюстрированная книга о сексе.

Костюмы туда не входят, потому что одежда относится к гардеробу.

Массажное масло остается обычным item; его интерфейсная категория определяется текущей общей системой inventory и не должна насильно считаться интимным товаром.

Вкладка не создает копии items.

### 7. Разделить владение, обычное хранение и текущее runtime-состояние

У item есть единая сущность и владение, например:

```text
owns(item_id)
```

При этом текущее физическое состояние экземпляра может меняться, например:

```text
remote_toy
owner: Nastya
current_state: inventory
```

или:

```text
remote_toy
owner: Nastya
current_state: body
```

Это не создает второй item.

Поле/модель `storage` описывает обычное место хранения, а runtime-state — текущее физическое состояние экземпляра.

### 8. Развести способы использования items

Не считать все `usable` items одинаковыми.

Минимально предусмотреть два режима:

#### `action_tool`

Предмет используется внутри действия или сцены. После завершения действия многоразовый предмет остается в inventory и не получает длительного body-state только потому, что физически использовался внутри сцены.

Текущие примеры:

- `bullet_vibrator`;
- `vacuum_stimulator`;
- `dildo`;
- `vibrator`;
- `anal_beads`;
- `soft_handcuffs`;
- `strapon`.

Типичный поток:

```text
inventory
→ action/scene
→ item временно используется
→ action/scene заканчивается
→ item остается в inventory
```

#### `persistent_body_item`

После отдельного действия предмет может оставаться физически установленным на/в теле между действиями, сценами и локациями до явного снятия/извлечения или сюжетного события.

Текущие примеры:

- `anal_plug`;
- `tail_plug`;
- `remote_toy`.

Один item при необходимости может поддерживать несколько `use_modes`, но режимы определяются карточкой конкретной вещи, а не всей категорией секс-игрушек.

### 9. Выбор предмета через действие

Действие может предлагать доступные способы/предметы.

Пример системной логики:

```text
Кровать
→ Мастурбация
   → руками
   → вибропуля
   → вибратор
   → дилдо
```

Меню показывает только варианты, которые:

- принадлежат Насте;
- физически доступны;
- совместимы с действием;
- соответствуют раскрепощенности;
- разрешены текущим сюжетом/контекстом.

После использования многоразовый action tool не расходуется и остается в inventory.

### 10. Не заставлять item знать все будущие сцены

По возможности action/event должен запрашивать подходящие предметы по типу/capability/tag, а не требовать жестко прошивать в каждой item-card все возможные сцены.

Например:

```text
action = masturbation
compatible capability = masturbation_tool
```

Точная реализация должна использовать/расширять существующий action/event contract, если он уже решает эту задачу.

### 11. Persistent body item: установка

Persistent item может быть установлен двумя равноправными путями.

**Из inventory:**

```text
Инвентарь
→ Интимное
→ Дистанционный вибратор
→ Использовать
→ Вставить
```

**Как результат action/event/scene:**

```text
action/event
→ item используется
→ результат оставляет item установленным
```

Оба пути обязаны приводить к одному runtime-state. Не создавать отдельную копию вроде `remote_toy_inserted_copy`.

### 12. Persistent body item: снятие

Установленный item остается активным до явного снятия/извлечения либо сюжетного события, которое это делает.

Типичный поток:

```text
inventory
→ вставить
→ body
→ действия / переходы / события
→ вынуть
→ inventory
```

После снятия тот же item возвращается в обычное состояние inventory.

### 13. `remote_toy`

Фиксируется как **носимый дистанционно управляемый вибратор, который вставляется и может оставаться внутри между действиями и локациями**.

Он должен:

- вставляться непосредственно из inventory;
- устанавливаться в результате действия/сцены;
- сохранять установленное состояние при переходах между локациями;
- иметь доступное event/action-condition состояние;
- потенциально влиять на срабатывание других событий;
- после извлечения возвращаться в обычный inventory-state.

Конкретная форма корпуса, внешний дизайн, точная схема управления и уровни/режимы работы остаются `TBD`, пока отдельно не утверждены.

### 14. `anal_plug`

Анальная пробка является persistent body item и может оставаться установленной между действиями и локациями.

### 15. `tail_plug`

Пробка с хвостиком является persistent body item и может оставаться установленной между действиями и локациями.

Видимый хвост является частью того же item, а не отдельной сущностью.

### 16. `anal_beads`

Анальные бусы являются обычным action tool.

Они не создают длительное состояние между действиями/локациями и не получают постоянный HUD-status.

### 17. `vibrator`

Обычный вибратор является action tool.

Он хранится в inventory, выбирается внутри подходящего действия, используется в сцене и после нее остается в inventory.

Не использовать универсальное `equip` для всех секс-игрушек.

### 18. `soft_handcuffs`

Мягкие наручники не являются wearable/persistent body item.

Они могут использоваться как:

- предмет действия;
- реквизит сцены;
- условие квеста;
- требуемый предмет события.

После сцены остаются в inventory, если конкретный сюжет прямо не меняет владение.

Не выводить наручники в persistent status HUD только потому, что они использованы внутри сцены.

### 19. Persistent items должны быть доступны event/action/quest conditions

Состояние установленного item должно читаться общей системой условий, например семантически:

```text
body_item_active("remote_toy")
```

или через эквивалентный существующей архитектуре API.

Это должно позволять:

- открывать события;
- изменять варианты событий;
- добавлять реакции;
- блокировать/разрешать действия;
- запускать scripted events.

Не создавать отдельный boolean для каждого item, если состояние уже выводится из единой модели items.

## Единый гардероб

### 20. Один гардероб

Изменить концепцию: в игре существует **один гардероб Насти**, а не независимые домашний, рабочий и иные гардеробы.

Не создавать отдельные коллекции принадлежащих Насте вещей:

```text
home_wardrobe
cafe_wardrobe
shop_wardrobe
```

как самостоятельные владельцы одних и тех же предметов.

### 21. Гардероб доступен только в разрешенных местах/ситуациях

Единый wardrobe UI/система открывается только там, где физически допускается или требуется переодевание/раздевание/одевание.

Примеры допустимых access points:

- комната Насти;
- подсобка или служебное помещение;
- раздевалка;
- место работы с возможностью переодеться;
- иной специально разрешенный контекст;
- scripted-сцена переодевания.

Точный перечень wardrobe access points задается конкретными локациями/сценами и не должен глобально разрешать переодевание где угодно.

### 22. Место доступа не создает отдельный гардероб

Открытие wardrobe в комнате, подсобке или другом разрешенном месте использует одну систему вещей.

Текущий контекст при этом может:

- разрешать только часть вещей;
- блокировать отдельные варианты;
- разрешать рабочие варианты;
- требовать определенный комплект;
- разрешать частичное раздевание;
- запрещать неподходящую одежду.

Это контекстные правила/фильтрация, а не отдельное хранилище.

### 23. Одна одежда — одна сущность

Любая физическая вещь определяется один раз.

Например `waitress_costume` остается одним item, когда Настя:

- носит его дома;
- использует в ролевой ситуации;
- фотографируется;
- работает в кафе.

Не создавать:

```text
waitress_costume_home
waitress_costume_work
waitress_costume_photo
```

### 24. Сюжетное открытие нового контекста

Владение вещью не означает автоматическое разрешение использовать ее во всех сценариях.

После покупки `waitress_costume` находится в едином гардеробе Насти, но работа в нем в кафе может быть изначально запрещена.

Позже сюжетный unlock вроде:

```text
cafe_waitress_costume_work_unlocked
```

или эквивалент разрешает использовать **тот же item** в рабочем контексте. Флаг не создает новую копию вещи.

### 25. Правило для всех четырех ролевых костюмов

Принцип единой сущности применяется к:

- `schoolgirl_costume`;
- `maid_costume`;
- `waitress_costume`;
- `nurse_costume`.

Каждый существует один раз и может позже получать дополнительные сценарные разрешения: работа, фотосессия, мероприятие, квест, ролевая сцена или иной контекст.

### 26. Одежда работодателя

Система должна поддерживать одежду, которая физически принадлежит месту работы, а не Насте.

Такая вещь:

- использует ту же item-модель;
- доступна только там, где физически находится;
- может показываться в том же wardrobe UI при наличии доступа;
- не становится собственностью Насти;
- не появляется автоматически в других местах.

То есть интерфейс/система wardrobe едины, но ownership и physical availability учитываются отдельно.

### 27. Раздевание и пустые слоты

Система должна поддерживать:

- надевание;
- снятие;
- пустые слоты;
- частичное отсутствие одежды;
- полное отсутствие одежды.

Не создавать фиктивные items `topless_item`, `nude_item` и подобные. Отсутствие одежды определяется состоянием обычных технических слотов.

### 28. Bright Past не является обязательным UI-макетом

Владелец рассматривает UX-идею Bright Past как референс, но окончательный wardrobe UI пока не утвержден.

В TASK фиксируется только архитектурный фундамент:

- единый wardrobe;
- ограниченные точки доступа;
- одна сущность вещи;
- контекстные разрешения;
- отсутствие копий.

Не утверждать самостоятельно конкретные вкладки, preset/outfit UX или точную компоновку гардероба.

## UI / UX

### 29. Status HUD сверху слева

Предусмотреть компактную панель состояний **сверху слева**.

Она показывает маленькие значки текущих значимых состояний Насти. При наведении на значок показывается tooltip с названием и кратким описанием/последствием состояния.

Панель не должна занимать большой экранный объем и должна соответствовать `UI_VISUAL_SYSTEM_SPEC.md`. Финальные иконки не заменять emoji/Unicode-заглушками.

### 30. HUD не хранит состояние

HUD только отображает готовое состояние систем-владельцев.

Не создавать параллельные `is_tired`, `is_bad_mood`, `is_max_aroused`, `has_plug_status` и аналогичные дубли, если значение можно получить из текущих характеристик или item-state.

### 31. Только критические/пиковые состояния

Панель не показывает нормальные и промежуточные значения.

Для каждого существующего игрового параметра показывается максимум один status icon. Не создавать несколько severity-иконок одного параметра.

### 32. Усталость

Текущая энергия имеет диапазон `0…10`.

Утвержденный HUD-порог:

```text
energy <= 1
→ status icon "Устала"
```

При `energy >= 2` значка нет.

Tooltip может показывать текущее значение, например `Энергия почти закончилась: 1/10`.

### 33. Голод

Для голода используется один HUD-status:

`Голодна`.

Не использовать разные HUD-уровни `Голодна` / `Очень голодна`.

Точный порог появления должен опираться на уже существующую механику голода. Если внутри игровой логики разные степени голода используются для механики, не удалять их автоматически: изменить только HUD-представление, если это разные уровни ответственности.

Текущий `HUD_TEMPORARY_EFFECTS_SPEC.md`, где присутствуют `hungry` и `very_hungry` как разные severity для HUD, необходимо синхронизировать с этим решением.

### 34. Возбуждение

HUD показывает возбуждение только при максимальном существующем значении.

Текущий runtime использует `arousal = 0…3`, поэтому при актуальной реализации:

```text
arousal == 3
→ status icon пикового возбуждения
```

Рабочее отображаемое название: `Перевозбуждена`. Если при UI-полировке владелец утвердит другое короткое название, изменить только UI-label, не механику.

Не показывать в верхней status panel промежуточные значения `слегка возбуждена` / `возбуждена`.

### 35. Настроение

При отрицательном существующем состоянии `mood` выводится единый значок `Плохое настроение`.

При нормальном и положительном mood значка нет.

Не вводить дополнительные уровни плохого настроения ради HUD.

### 36. Persistent body items в HUD

Каждый реально установленный persistent body item отображается отдельным значком все время, пока item остается установленным.

Текущие примеры:

- `anal_plug`;
- `tail_plug`;
- `remote_toy`.

Tooltip сообщает, какой item установлен, и при необходимости его текущее активное состояние.

Если позднее `remote_toy` получит состояния включен/выключен/режим, tooltip может их отображать без создания нового item.

### 37. Action tools не выводятся как persistent status

Не показывать в status HUD только из-за текущей сцены:

- обычный вибратор;
- дилдо;
- анальные бусы;
- наручники;
- лубрикант;
- другие временные action tools.

HUD показывает долгоживущие состояния между обычными действиями, а не каждый временно используемый реквизит.

### 38. Состояние persistent item в inventory UI

Установленный persistent item желательно продолжать показывать во вкладке `Интимное`, но с marker/status `Установлен`/эквивалентом.

Не показывать вторую копию item.

### 39. Действие карточки зависит от состояния

Для persistent item UI-команда должна соответствовать физическому действию.

Например:

```text
remote_toy / inventory
→ Вставить
```

после установки:

```text
remote_toy / body
→ Вынуть
```

Не использовать абстрактное `Экипировать` как обязательный пользовательский текст для всех типов предметов.

## Раскрепощенность и доступность

### 40. Разделить покупку и использование

У item должны независимо существовать:

```text
required_openness_purchase
required_openness_use
```

Покупка предмета не означает автоматическую готовность применить его.

### 41. Action/event gate не обходится вспомогательным item

Например, низкий `required_openness_use` лубриканта не означает, что наличие лубриканта позволяет выполнить сексуальное действие более высокого уровня.

Само действие проверяет собственные requirements.

### 42. Владение одеждой не равно разрешению контекста

Настя может:

1. владеть костюмом;
2. иметь право надевать его дома;
3. еще не иметь права работать в нем.

То есть:

```text
ownership != generic use != context permission
```

## Примечания для исполнителя

Главные архитектурные инварианты:

> **Одна физическая вещь — одна item-сущность.**

> **Один гардероб — несколько разрешенных точек доступа и контекстов.**

> **Инвентарная вкладка — это фильтр, а не отдельное хранилище.**

> **Action tool существует только внутри действия; persistent body item сохраняет состояние между действиями/локациями.**

> **HUD показывает только значимое состояние, но не становится владельцем этого состояния.**

> **Никаких параллельных boolean-флагов, копий item, отдельных work/home wardrobe и специальных inventory без реальной необходимости.**

Перед кодом обязательно проверить существующую реализацию и расширять ее вместо создания параллельной системы.
