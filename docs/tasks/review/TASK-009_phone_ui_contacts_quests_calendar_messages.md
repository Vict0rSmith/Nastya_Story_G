# TASK-009 — Телефон: smartphone UI, контакты, задания, календарь и сообщения

## Цель

Переработать существующий интерфейс телефона так, чтобы он визуально воспринимался как современный смартфон, а основные приложения были полноценными игровыми интерфейсами вместо прототипных текстовых экранов.

В рамках TASK реализовать:

1. новую предметную оболочку телефона и домашний экран;
2. приложение `Контакты`;
3. приложение `Задания`;
4. приложение `Календарь`;
5. приложение `Сообщения`;
6. общую внутреннюю навигацию телефона;
7. необходимые runtime-данные и интеграции перечисленных приложений.

**Банк в TASK не входит.**

## Основание

Актуальный `UI_VISUAL_SYSTEM_SPEC.md` требует предметную оболочку современного смартфона, правдоподобный корпус и экран, статусную строку и безопасные поля, регулярную сетку приложений, единые внутренние компоненты списков и заголовков и отсутствие вида обычного Ren'Py modal window. Визуальный ориентир — `assets/ui/approved_references/phone.png`.

Текущая реализация `phone_screen` визуально этим требованиям не соответствует и содержит прототипные интерфейсы приложений.

Дополнительные требования настоящего TASK утверждены владельцем 2026-09-08.

Перед кодированием синхронизировать затронутые канонические спецификации с утвержденными ниже решениями, если этих требований в них еще нет. TASK не должен становиться параллельным владельцем постоянной механики.

## Gate перед началом реализации

Перед переводом в `in_progress`:

1. предыдущий TASK должен быть принят владельцем;
2. публикация принятой предыдущей работы должна быть завершена;
3. локальная каноническая `main` и GitHub `main` должны быть синхронизированы по актуальному `DEVELOPMENT_WORKFLOW.md`;
4. не должно быть состояния `SYNC PENDING`.

Перед началом выполнить актуальную safe Git-проверку по `AGENTS.md` / `DEVELOPMENT_WORKFLOW.md`.

## Что реализовать

### 1. Архитектура телефона

Не наращивать все внутри одного монолитного `phone_screen`.

Существующий внешний entry point можно сохранить, но внутренние приложения разделить на самостоятельные screens/components либо эквивалентную чистую структуру.

Ожидаемое разделение по ответственности:

```text
phone_screen
phone_home
phone_contacts
phone_contact_card
phone_quests
phone_quest_card
phone_calendar
phone_messages
phone_chat
```

Точные технические имена могут быть другими, если они лучше соответствуют существующему naming convention.

Не создавать параллельное хранилище игровых сущностей только ради UI.

### 2. Общая оболочка смартфона

Телефон должен визуально восприниматься именно как современный смартфон.

Обязательные признаки:

- затемнение игрового мира за телефоном;
- отдельный визуально правдоподобный корпус смартфона;
- округленный внешний корпус;
- отдельная область экрана внутри корпуса;
- верхняя status bar;
- безопасные верхнее и нижнее поля;
- единая внутренняя геометрия всех приложений;
- визуальная иерархия по `UI_VISUAL_SYSTEM_SPEC.md`;
- опора на `assets/ui/approved_references/phone.png`, без pixel-perfect копирования;
- домашний экран с регулярной сеткой иконок приложений;
- приложения не должны выглядеть как набор обычных Ren'Py textbuttons на большой прямоугольной панели.

Убрать нынешнее ощущение обычного modal window.

#### Навигация

Нужна единая понятная телефонная навигация:

- переход на домашний экран;
- возврат назад из карточки/чата к родительскому экрану;
- закрытие телефона;
- сохранение общей геометрии при переключении приложений.

Не использовать несогласованные текстовые навигационные элементы, если для функции должен применяться functional icon по Design System.

Существующее управление состоянием телефона использовать или аккуратно расширить, а не создавать параллельную систему.

### 3. Домашний экран

Разместить в регулярной сетке доступные приложения.

В рамках этого TASK полноценно реализуются:

- `Контакты`;
- `Задания`;
- `Календарь`;
- `Сообщения`.

Существующие приложения вне TASK не удалять самовольно.

#### Банк

`Банк` **не реализовывать и не перерабатывать функционально в TASK-009**.

Если он остается на домашнем экране:

- сохранить его как явно незавершенное/недоступное приложение;
- не маскировать placeholder под готовое приложение;
- не создавать финансовую архитектуру, доходы, расходы, кредиты или долги.

#### Другие приложения

Камера, галерея, карта, университетское приложение и иные существующие/будущие приложения:

- не реализовывать только ради этого TASK;
- не удалять существующую рабочую интеграцию;
- сохранить текущие unlock/placeholder-контракты, если они существуют.

## Контакты

### 4. Список контактов

Приложение открывается экраном списка известных контактов.

Каждая строка содержит:

- фото/аватар;
- ФИО либо каноническое имя персонажа в доступной Насте форме;
- краткую подпись, например `Подруга`, `Соседка`, `Однокурсница` или другую канонически корректную связь.

**Поиска контактов не делать.**

Не показывать персонажа, который еще не известен Насте как контакт.

Не раскрывать сведения, которые персонаж игрока еще не знает.

### 5. Карточка контакта

По нажатию строки открывается карточка персонажа.

Карточка должна содержать в подходящем для персонажа объеме:

- фото/портрет;
- имя;
- характер связи;
- игровые характеристики, которые разрешено показывать;
- текущие отношения в соответствии с существующей relationship model;
- известные Насте факты о персонаже.

Не превращать телефонную карточку в полный debug/canon-паспорт NPC.

Известные факты должны быть runtime-aware: если факт еще не открыт игроку, он не показывается.

#### Действия

В карточке контакта предусмотреть кнопки:

- `Позвонить`;
- `Написать`.

`Написать` открывает чат с этим контактом.

Для `Позвонить` в рамках TASK достаточно корректного UI/runtime hook к системе звонков. Если полноценная механика телефонных звонков еще не определена каноном, не придумывать ее: оставить архитектурно корректный hook / disabled-state с явной причиной.

Не создавать сюжет звонка без утвержденного контента.

## Задания

### 6. Основной экран заданий

Приложение содержит три вкладки:

- `Активные`;
- `Выполненные`;
- `Проваленные`.

Каждая вкладка показывает только соответствующие задания.

### 7. Строка задания

В списке показывать короткий блок/строку с **названием задания**.

Отдельную строку с текстовым статусом `Активно` / `Выполнено` / `Провалено` **не показывать**, потому что статус уже однозначно определяется выбранной вкладкой.

Не дублировать одну и ту же информацию ради визуальной симметрии.

### 8. Карточка задания

По нажатию открывается полная карточка задания.

Показывать существующие канонические/runtime-данные задачи, по применимости:

- название;
- полное описание;
- текущие цели/этапы;
- выполненные этапы;
- дополнительные условия;
- срок или значимую дату, если она существует в данных.

Не придумывать награды, сроки или дополнительные поля, отсутствующие в каноне/runtime.

Использовать существующую quest architecture, а не копировать задания в отдельную телефонную базу.

## Календарь

### 9. Месячный вид

Календарь должен выглядеть как обычный календарь текущего месяца.

Обязательная структура:

- название месяца;
- год;
- кнопка предыдущего месяца;
- кнопка следующего месяца;
- строка дней недели;
- сетка календарных дней;
- корректное размещение первого дня месяца;
- корректное число дней;
- выделение текущего игрового дня.

Переключение месяца не изменяет игровую дату.

### 10. Выходные

Суббота и воскресенье должны визуально отличаться от рабочих дней.

Использовать семантику Design System, не вводить случайные цвета непосредственно в screen.

### 11. Значимые даты

Календарь должен поддерживать отображение:

- официальных праздников, если они внесены в канонические данные игры;
- известных Насте дней рождения персонажей;
- иных известных знаковых дат;
- квестовых/сюжетных дат.

Если событие неизвестно Насте, оно не должно появляться как спойлер.

#### Отображение

При наличии значимой даты:

- **цветом выделяется ячейка с датой**;
- при hover/focus отображается компактный tooltip;
- tooltip кратко поясняет событие.

Если на одну дату приходится несколько событий, tooltip должен корректно показать их без потери информации и без ломания сетки календаря.

Не выводить длинные описания непосредственно в ячейку календаря.

### 12. Источник календарных событий

Не захардкодить конкретный список событий непосредственно в `phone_calendar_screen`.

Сделать данные/adapter так, чтобы календарь мог получать события из существующих сущностей и будущих источников.

Если для праздников, дней рождения или quest dates в проекте еще нет общего канонического владельца, при реализации:

1. определить подходящий существующий системный владелец;
2. расширить его;
3. не создавать несколько конкурирующих календарей событий.

Не придумывать отсутствующие даты: `TBD` остается `TBD`.

## Сообщения

### 13. Общий вид

Приложение должно визуально напоминать упрощенный современный мессенджер.

Не требуется имитировать конкретный коммерческий мессенджер.

### 14. Список диалогов

На первом экране показывать список диалогов.

Каждая строка:

- аватар контакта;
- имя;
- превью последнего сообщения;
- при необходимости — индикатор непрочитанного сообщения.

Не показывать отдельный глобальный список всех контактов вместо списка чатов.

Если чат еще никогда не существовал, открытие нового диалога допускается через карточку контакта → `Написать`.

### 15. Экран чата

Показывать историю сообщений в хронологическом порядке.

Вместо свободного произвольного ввода игрок выбирает доступную реплику/действие из списка.

Поддержать два класса исходящих сообщений.

#### 15.1. Сюжетные сообщения

Появляются по условиям квеста/события.

Могут:

- открывать или продолжать сюжет;
- менять флаги;
- влиять на отношения;
- вызывать ответ NPC.

Не создавать новые сюжетные сообщения или тексты только ради наполнения интерфейса.

#### 15.2. Бытовые сообщения

Минимально предусмотреть системные варианты вроде:

- `Как дела?`
- `Что делаешь?`

Архитектура должна позволять расширить их позже без переписывания screen.

Для бытового сообщения NPC выбирает ответ из подходящего набора вариантов.

При подборе ответа учитывать доступный runtime-контекст, прежде всего:

- текущую локацию NPC;
- время/период дня, если это необходимо конкретному пулу;
- доступность NPC;
- иные существующие состояния, если они уже являются реальной зависимостью.

Пример: ответ на `Что делаешь?` должен иметь возможность зависеть от фактического местоположения персонажа, а не от случайной строки, противоречащей runtime.

Ответ выбирается случайно из **подходящего** пула, а не из всех вариантов подряд.

### 16. Cooldown бытовых сообщений

Несюжетные бытовые сообщения ограничиваются cooldown.

Cooldown:

- применяется к бытовым сообщениям;
- не должен блокировать обязательное сюжетное сообщение;
- должен иметь понятный disabled-state/объяснение игроку;
- должен храниться в runtime/save-safe состоянии.

**Точная длительность cooldown владельцем пока не определена.**

Не выбирать число самостоятельно.

Если существующая спецификация уже содержит утвержденное значение — использовать его.

Если значения нет — оставить параметр `TBD` в каноне и реализовать конфигурируемую механику без самовольного балансного значения либо остановиться за конкретным решением, если без значения невозможно корректно завершить runtime.

### 17. Данные сообщений

Не хранить все содержимое сообщений внутри screen.

Разделить:

- данные/правила доступности;
- историю чата;
- presentation.

Не создавать вторую независимую модель NPC только ради сообщений.

Использовать существующее определение местоположения/расписания NPC.

## Данные и сущности

### 18. Phone UI state

Допускается расширить UI-state телефона для:

- текущего приложения;
- выбранного контакта;
- выбранного задания;
- отображаемого месяца;
- выбранного чата;
- внутреннего navigation state.

UI-state не должен дублировать игровые факты.

### 19. Persistent/save state

Если TASK требует нового сохраняемого gameplay-state, например:

- историю сообщений;
- unread-state;
- cooldown;
- известные телефонные контакты/открытые факты, если их еще не покрывает текущий story state,

сначала проверить существующую архитектуру `game_state` и save schema.

Расширять существующую систему.

Не создавать глобальные Python-переменные, которые теряют состояние после save/load, если информация является частью прохождения.

При изменении save schema добавить применимую migration/regression проверку.

### 20. Knowledge gate

Единый принцип для телефона:

> Телефон показывает информацию, которой Настя фактически располагает на текущем этапе прохождения.

Это относится к:

- контактам;
- фактам персонажей;
- дням рождения;
- квестовым датам;
- сообщениям.

Телефон не является debug-энциклопедией и не должен раскрывать будущий контент.
