# Задания реализации — карта раздела

Это очередь **реализации**, а не канон дизайна. Проектные решения сначала фиксируются в соответствующих `docs/systems/`, `docs/world/` или `docs/content/`, затем TASK ссылается на них.

TASK может исполнять любой ИИ-исполнитель (Grok Bot, ChatGPT, Codex и другие) в соответствии с [`../DEVELOPMENT_WORKFLOW.md`](../DEVELOPMENT_WORKFLOW.md). Само наличие `.rpy`, нескольких файлов или runtime/UI-изменений не делает Codex обязательным исполнителем.

## Когда нужен TASK

TASK создается для заметной работы, которую полезно сохранять как самостоятельную единицу истории разработки. Обычно это:

- новая или существенно меняемая игровая система;
- изменение нескольких связанных файлов с отдельными критериями приемки;
- изменение save schema, состояния игры или публичного API системы;
- новый/существенно измененный screen, HUD-поток, UI-механика, квест или игровой маршрут;
- реализация, для которой нужен отдельный Context Manifest и проверяемый набор требований;
- работа, которую полезно отдельно провести через `in_progress → review → done` независимо от исполнителя.

Мелкая локальная правка не обязана получать TASK. Она может выполняться по прямому поручению владельца с обычным Git-коммитом/PR и итоговым отчетом. Если правка меняет статус системы или ближайшую работу, все равно проверить Board/Roadmap.

Главный критерий: **TASK нужен из-за значимости и самостоятельности работы, а не из-за выбора исполнителя**.

## Учет исполнения

В новом или существенно переработанном TASK используются поля из [`../templates/TASK_TEMPLATE.md`](../templates/TASK_TEMPLATE.md):

- `executor` — фактический основной исполнитель;
- `verification_level` — `REMOTE_LIMITED` или `FULL_LOCAL`;
- `implementation_commits` — commit SHA реализации;
- `implementation_report` — ссылка на отдельный отчет, если он вынесен из TASK.

Перед `review` исполнитель заполняет Implementation report: результат, измененные файлы, реально выполненные и непроведенные проверки, известные проблемы и коммиты.

`REMOTE_LIMITED` допускает передачу в `review`, если реализация выполнена и доступные проверки пройдены. В `done` TASK переводится после требуемой проверки и принятия владельцем; владелец может явно принять результат без полного локального прогона.

Принятие/перевод в `done` включает обязательную Git-публикацию и синхронизацию канонической локальной `main` по [`DEVELOPMENT_WORKFLOW.md`](../DEVELOPMENT_WORKFLOW.md). В отчете фиксировать общий SHA либо `SYNC PENDING` с блокером. До устранения незавершенной синхронизации не начинать следующий TASK; немедленно сообщать владельцу причину.

## Перед выбором или исполнением TASK

Обязательно открыть:

1. [`../DEVELOPMENT_BOARD.md`](../DEVELOPMENT_BOARD.md);
2. конкретный TASK;
3. его Context Manifest и только минимальный стартовый контекст;
4. при необходимости [`../DEVELOPMENT_WORKFLOW.md`](../DEVELOPMENT_WORKFLOW.md).

Жизненный цикл:

`backlog → ready → in_progress → review → done`

- [`backlog/`](backlog/) — идея или незавершенное проектирование; не реализовывать;
- [`ready/`](ready/) — требования утверждены;
- [`in_progress/`](in_progress/) — текущая реализация;
- [`review/`](review/) — ожидает проверки/приемки;
- [`done/`](done/) — принято владельцем.

## Context Manifest

Каждый новый или существенно переработанный TASK содержит:

- `READ REQUIRED`;
- `CODE REQUIRED`;
- `READ IF NEEDED`;
- `DO NOT SCAN`;
- `CHECKS`.

Manifest задает стартовый набор, но не запрещает открыть реально обнаруженную зависимость.

Если TASK создает, дописывает или существенно редактирует игровой текст, он дополнительно использует условный **Content Authoring Context** из [`../templates/TASK_TEMPLATE.md`](../templates/TASK_TEMPLATE.md) и включает в `READ REQUIRED`:

- [`../content/WRITING_BRIEF.md`](../content/WRITING_BRIEF.md) (длинные гайды — по нужде, как указано в брифе);
- карточки реально участвующих персонажей.

Content Authoring Context передает конкретный режим/сцену/участников/обязательные факты и применимый progression/override context, но **не копирует художественные гайды или character canon**.

Обсуждение в TASK-подготовке само по себе не включает режим «пишу текст игры». Он включается, когда поручение требует создать или заметно отредактировать фактический игровой контент. Технический перенос уже утвержденного текста идет в режиме «переношу утвержденный текст».

Шаблон Manifest: [`../templates/CONTEXT_MANIFEST_TEMPLATE.md`](../templates/CONTEXT_MANIFEST_TEMPLATE.md).

## Актуализация планов

При переводе TASK между стадиями проверить:

- [`../DEVELOPMENT_BOARD.md`](../DEVELOPMENT_BOARD.md);
- [`../IMPLEMENTATION_ROADMAP.md`](../IMPLEMENTATION_ROADMAP.md), если изменился фактический статус системы/направления.

Board и Roadmap не являются источниками требований.

## Проверка Ren'Py TASK

Для TASK, затрагивающего `.rpy`, runtime, screens/UI, labels/jumps/calls, characters или asset references, применяется [`../RENPY_MCP_WORKFLOW.md`](../RENPY_MCP_WORKFLOW.md):

- `FULL_LOCAL` — применимые diagnostics → Ren'Py lint → preview/runtime;
- `REMOTE_LIMITED` — доступные GitHub/diff/code-search/CI/dependency checks с явным перечислением непроведенных локальных проверок.

`REMOTE_LIMITED` не является автоматическим основанием менять исполнителя.

Шаблон TASK: [`../templates/TASK_TEMPLATE.md`](../templates/TASK_TEMPLATE.md). Правила AI: [`../../AGENTS.md`](../../AGENTS.md).
