# Ren'Py MCP — регламент проверки и запуска

Статус: **технический рабочий регламент**.

Этот документ определяет, как ChatGPT и Codex проверяют изменения Nastya Story, затрагивающие Ren'Py, и как используется подключенный Ren'Py MCP (`fracturedring/renpy-mcp`) при доступном локальном контуре.

Ren'Py MCP **не является источником канона, дизайна или игровых требований**. Канон и требования берутся только из актуального репозитория Nastya Story по правилам `AGENTS.md`, `MASTER_SPEC.md`, тематических MOC и TASK/прямого поручения владельца.

## 1. Роль MCP в проекте

Для Nastya Story MCP используется прежде всего как **слой чтения, диагностики, lint и запуска Ren'Py**.

Основная полная схема:

`TASK/прямое поручение/спецификации → реализация → MCP-диагностика → Ren'Py lint → preview/launch → отчет`

MCP не заменяет Git, каноническую документацию, TASK и обычную работу исполнителя с файлами.

Если локальный компьютер, MCP или Ren'Py SDK в момент работы недоступны, применяется режим `REMOTE_LIMITED` из `DEVELOPMENT_WORKFLOW.md`: реализация не блокируется автоматически, но локальные проверки не считаются выполненными.

## 2. Когда нужен полный локальный Ren'Py-контур

При доступном локальном окружении полный контроль применяется к изменениям, которые затрагивают:

- `.rpy`-код;
- labels, jumps, calls и сюжетную навигацию;
- characters и speaker definitions;
- screens и UI;
- image/audio references;
- игровые сцены, которые должны запускаться в Ren'Py;
- добавление/удаление/переименование Ren'Py-сущностей;
- изменения состояния/сохранений, способные сломать загрузку или runtime;
- любые изменения, способные сломать запуск или lint проекта.

Для чисто документационных правок в `docs/`, не затрагивающих реализацию, MCP не требуется.

## 3. Preflight перед изменениями

Исполнитель сначала проверяет актуальное состояние GitHub/рабочей копии по `AGENTS.md` и `DEVELOPMENT_WORKFLOW.md`.

Если локальный MCP доступен, необходимо убедиться, что он привязан именно к текущему проекту Nastya Story.

Запрещено использовать `new_project` для Nastya Story: проект уже существует и не должен пересоздаваться или scaffold-иться в отдельную папку.

Перед значимым изменением доступные read/introspection-инструменты MCP используются только в объеме, необходимом текущей задаче, например:

- обзор проекта;
- список/чтение затрагиваемых labels;
- список screens;
- characters;
- images/audio;
- существующие переходы и зависимости.

Цель preflight — подтвердить фактическое состояние реализации перед правкой и не создавать дубликаты уже существующих сущностей.

Если локальный MCP недоступен, preflight выполняется через актуальные GitHub-файлы, code search, спецификации и прямые зависимости; это должно быть отражено как `REMOTE_LIMITED`.

## 4. Проверки после изменений при `FULL_LOCAL`

После изменения Ren'Py-кода и при доступном локальном контуре выполняется следующий контрольный цикл.

### 4.1. Статические MCP-диагностики

Запускать применимые проверки из доступного набора MCP, включая по необходимости:

- `find_invalid_jumps` — переходы на несуществующие labels;
- `find_undefined_characters` — использование неопределенных персонажей;
- `find_unused_characters` — подозрительно неиспользуемые определения персонажей;
- `find_missing_assets` — отсутствующие image/audio assets;
- `find_undefined_screens` — вызовы отсутствующих screens;
- `find_unreachable_labels` — недостижимые labels.

Не требуется механически запускать нерелевантную проверку, если задача заведомо не затрагивает соответствующую область. Для крупных рефакторингов и новых игровых маршрутов предпочтителен полный набор.

Если диагностика находит проблему, появившуюся из-за текущей работы, исполнитель исправляет ее до завершения проверки.

Существующие ранее проблемы вне области задачи не исправляются самовольно: их нужно перечислить отдельно в отчете.

### 4.2. Ren'Py lint

Перед завершением `FULL_LOCAL`-проверки любой реализации, затрагивающей `.rpy`, обязателен `get_lint_report` либо эквивалентный полноценный Ren'Py lint.

Требование к результату:

- новых lint errors быть не должно;
- ошибки, вызванные текущей работой, должны быть устранены;
- существующие внешние ошибки, если они блокируют проверку, должны быть явно отражены в отчете.

Фраза «код выглядит корректно» не заменяет lint.

### 4.3. Preview / запуск

Для изменений, меняющих видимый игроку результат или runtime-поведение, после успешного lint требуется запуск через `launch_preview` либо эквивалентный локальный инструмент.

После запуска проверить статус через `get_preview_status` либо эквивалентный механизм.

К этой категории относятся минимум:

- UI/screens;
- HUD;
- сцены и диалоги;
- переходы между labels;
- меню и choices;
- навигация;
- действия игрока;
- инвентарь/гардероб/телефон;
- новые игровые системы с экранным поведением;
- миграции/изменения состояния, которые могут проявиться только при запуске или загрузке.

После проверки preview закрывается штатным инструментом, если он больше не нужен.

Автоматический Ren'Py runtime-тест, который действительно запускает измененный поток, является эквивалентным запуском; отдельный preview поверх того же сценария не обязателен. Для UI исполнитель дополнительно просматривает адресные кадры измененных состояний. Один только статус запуска или проверки размеров не доказывают отсутствие визуальных дефектов.

Локальный запуск подтверждает, что проект стартует и затронутый поток выполняется, но **не заменяет визуальную приемку владельцем**. Внешний вид, композицию, качество графики и соответствие approved visual references при необходимости проверяет владелец по реальному экрану/скриншоту.

## 5. Частота и объем проверок

### Выбор по изменению — одинаково для Codex и ChatGPT

Перед проверкой выбрать минимальный набор, достаточный для критериев TASK/поручения и реально затронутых зависимостей. `FULL_LOCAL` — уровень доступных средств, а не требование проверять все системы. Конкретный обязательный критерий TASK нельзя исключать ради экономии.

| Изменение | Минимальный применимый контроль |
| --- | --- |
| Только документация/отчет/доска | Diff, прямые ссылки и согласованность, применимый project health; Ren'Py не запускать |
| `.rpy`, labels, API, ссылки | Один итоговый lint; поиск измененных ID и соответствующая диагностика, без механического запуска всех MCP tools |
| Логика/данные/действия | Затронутые сценарии и их граничные условия; существующие `nastya_runtime`, `navigation`, `items_body_wardrobe` или отдельные testcases по риску |
| HUD/диалог/инвентарь/гардероб | Затронутые runtime-сценарии (`dialogue_layout`, `items_body_wardrobe` или нужные testcases), проверки геометрии/видимости и просмотр измененных экранов |
| Общий layout навигации/карта | `navigation` и при риске размеров `navigation_visual`; все 77 автоматических проверок допустимы без ручного просмотра всех кадров |
| Сохранения/миграция | Соответствующий тест миграции и требуемый сценарий сохранения/загрузки; чтение сериализованных данных не считать проверкой интерактивного `renpy.load`/`after_load` |
| Большой рефакторинг/общий старт | Расширить набор по зависимостям, зафиксировать причину; полный набор допустим при общем риске |

Новый тест добавлять для непокрытого значимого риска, а не ради увеличения числа проверок после выполнения критериев. Для большой реализации промежуточные дешевые проверки нужны после значимых изменений, окончательный релевантный цикл — после последней правки соответствующего кода.

### Краткий вывод и условие остановки

- В контекст исполнителя возвращать статус, выбранные тесты, число результатов, новые ошибки/предупреждения и путь к полному логу. Подробный лог хранить локально или в CI artifact; читать нужный фрагмент при ошибке. Не печатать весь успешный лог, списки пропущенных тестов, все пути снимков или большие неизмененные файлы.
- Успешный результат действителен для проверенного кода, зависимостей и конфигурации. Не повторять один и тот же lint через CLI и MCP ради второго зеленого отчета; повтор нужен при проверке самого MCP-транспорта, а не обычной игры.
- После успеха остановиться. Повторять затронутую проверку после исправления или появления конкретного нового риска; затем зависимые проверки, если исправление могло их затронуть. Изменение только отчета/статуса TASK не запускает новый игровой цикл.
- Существующие диагностические замечания классифицировать один раз и отмечать кратко; новые отличать от baseline. Проверять код завершения, а не только `clean`/пустой список findings. Не подавлять новые ошибки.

### Визуальная проверка

Автоматически проверить доступные размеры, видимость, отсутствие скрытых интерактивных элементов и корректность состояния. Затем открыть только значимые измененные состояния: обычно 1–3 кадра для небольшой UI-правки, больше — когда есть разные компоновки, длинные подписи, прокрутка, диалог/свободный режим или обнаруженная ошибка. Это ориентир, не жесткий лимит и не замена критериев.

Проверять наложения имени/текста, обрезание строк и крайних столбцов, границы контейнера и скроллбара, доступность кнопок, правильный режим HUD. После исправления смотреть исправленное состояние. Не уменьшать изображение до потери читаемости текста. Просмотр окна через computer use также передает кадры модели и не дает автоматической экономии относительно PNG. Создание локального файла само по себе не означает загрузку изображения в контекст.

### Команды Codex и удаленный маршрут ChatGPT

Локальный PowerShell runner: [`../tools/run_local_renpy_verify.ps1`](../tools/run_local_renpy_verify.ps1). По умолчанию выполняет один lint и `nastya_runtime`.

Runtime suites (`game/tests/`): `nastya_runtime` (базовый smoke), `navigation`, `navigation_visual`, `first_day`, `sleep_alarm`, `bank`, `dialogue_layout` (диалог и свободный режим), `items_body_wardrobe` (предметы, тело, гардероб, статусы, магазин, питание, миграция), `phone_suite` (телефон: контракты, сообщения, приложения, навигация, сохранение), `arousal_intimacy` (возбуждение, интимные действия, удаленная игрушка, сон), `ui_review` (HUD, действия NPC, квест и календарь в телефоне, системные меню).

Пример адресного запуска:

```powershell
./tools/run_local_renpy_verify.ps1 -RepoRoot T:/Nastya_Story_G -RenpySdkRoot T:/Renpy_SDK -Tests dialogue_layout,items_body_wardrobe
# Отдельный testcase (полное имя Ren'Py):
./tools/run_local_renpy_verify.ps1 -RepoRoot T:/Nastya_Story_G -RenpySdkRoot T:/Renpy_SDK -Tests 'items_body_wardrobe::wardrobe_runtime'
```

`-LintOnly` — только lint, когда runtime неприменим или уже проверен для того же кода; вывод явно содержит `NOT RUN`. `-DetailedReport` печатает подробности для диагностики. Полные логи сохраняются и в обычном режиме. Снимки создаются в новом подкаталоге каждого запуска; существующие файлы не удаляются, устаревшие кадры не считаются доказательством нового прогона. Отсутствие снимков допустимо для логических тестов; требуемые UI-кадры проверяются отдельно исполнителем.

Для ChatGPT предусмотрен [`Local Ren'Py verify`](../.github/workflows/local-renpy-verify.yml):

1. Проверить доступность workflow и self-hosted Windows runner, наличие `LOCAL_SYNC_ENABLED`, `NASTYA_LOCAL_REPO`, `RENPY_SDK_ROOT`; не настраивать их заново для каждой задачи.
2. При доступном инструменте запуска вызвать `workflow_dispatch` на нужном ref с `tests` (имена через запятую), при необходимости `lint_only`/`detailed_report`. Ветка должна содержать эти inputs. Автоматический push на `main` запускает только базовый `nastya_runtime`; это не полная проверка конкретного TASK. Не отправлять изменения в `main` только ради теста.
3. Прочитать краткий job summary: запрошенный и фактический SHA, исход, выбранные тесты. Проверять, что шаг реально выполнялся: зеленый workflow со skipped job не подтверждает runtime. При dirty/diverged checkout безопасная синхронизация может отказать; не обходить ее reset/очисткой.
4. При ошибке открыть соответствующий участок полного отчета. Для UI получить артефакт `renpy-verify-<sha>` и просмотреть только нужные кадры текущего запуска. Автоматическая загрузка артефакта в GitHub сама по себе не означает его просмотр моделью.
5. Записать `FULL_LOCAL` только при достаточном фактически выполненном локальном контуре (в том числе через runner) и требуемом просмотре UI. Если запуск, чтение артефакта или просмотр недоступны — указать точный пробел и применить `REMOTE_LIMITED` к неподтвержденной части. Отсутствие этих инструментов не запрещает реализацию ChatGPT.

Без runner ChatGPT адресно проверяет diff, ссылки/ID, условия видимости, размеры контейнеров с учетом spacing/scrollbar, сохранение контрактов и доступные CI checks. Статический анализ может найти часть наложений/обрезаний, но не заменяет фактический render. В отчет включить конкретный оставшийся экран/сценарий, не общий запрос «перепроверить всю игру».

## 6. Использование MCP для записи

Nastya Story **не принимает upstream-правило renpy-mcp о том, что все `.rpy`-изменения обязаны проходить только через MCP writer**.

Код может изменяться ChatGPT через GitHub или Codex в актуальной рабочей копии в соответствии с `AGENTS.md` и `DEVELOPMENT_WORKFLOW.md`.

Structured write tools MCP могут использоваться только если:

- они действительно удобнее для конкретной структурной операции;
- не противоречат TASK/прямому поручению;
- не создают параллельную архитектуру;
- исполнитель после этого все равно проверяет фактический Git diff.

Использование MCP Tier 4 (`apply_unified_diff`, `exec_python_in_init` и аналогичных escape-hatch инструментов) не является стандартным путем. Не включать/использовать Tier 4 без реальной необходимости; при архитектурно значимом применении зафиксировать это в отчете.

## 7. Что запрещено

Для Nastya Story через MCP нельзя:

- вызывать `new_project`;
- создавать отдельный scaffold вместо существующего проекта;
- считать MCP-данные источником канона;
- менять дизайн или механику потому, что MCP-инструменту так удобнее;
- автоматически исправлять все найденные warnings вне области задачи;
- генерировать отсутствующие игровые факты;
- считать успешный lint достаточной визуальной приемкой UI;
- скрывать диагностические ошибки через suppression только ради зеленого результата без обоснования.

## 8. Работа с ассетами

MCP может использоваться для проверки существования и корректности ссылок на assets.

Если задача включает новые графические/аудио assets, правила их производства задаются соответствующим TASK/проектной документацией, а не MCP.

Если используется регистрация изображения через MCP, предупреждения о media invariants должны быть проверены и отражены при необходимости.

Если задача прямо запрещает создание новых изображений, MCP не отменяет этот запрет.

## 9. Если локальный MCP / Ren'Py недоступен — `REMOTE_LIMITED`

Недоступность локального компьютера, self-hosted runner, MCP или Ren'Py SDK **не означает автоматическую передачу задачи Codex и не запрещает ChatGPT реализовать изменение через GitHub**, если способ реализации можно определить без локального запуска.

В режиме `REMOTE_LIMITED` исполнитель должен выполнить максимально доступные проверки:

1. проверить фактический Git diff и нужный контекст измененных участков; уже прочитанные неизменившиеся части повторно целиком не загружать;
2. через GitHub code search найти все известные использования измененных identifiers/API/events/screens и убедиться, что старые обращения не остались без причины;
3. проверить прямые зависимости по `REPOSITORY_MAP.md`, MOC и применимым спецификациям;
4. выполнить доступные repository/CI checks, включая `project_health_check`, если они действительно запускались;
5. проверить согласованность save schema/version, стартового состояния, UI labels/names, event names и других затронутых контрактов по коду;
6. перечислить локальные проверки, которые фактически не выполнялись.

При `REMOTE_LIMITED` запрещено писать:

- `Ren'Py lint passed`, если lint не запускался;
- `MCP diagnostics passed`, если MCP не использовался;
- `preview/runtime passed`, если проект не запускался.

Корректный статус: **«реализовано и удаленно проверено (`REMOTE_LIMITED`); полный локальный Ren'Py-контур не выполнен»**.

Это не считается автоматической ошибкой реализации. Когда локальное окружение снова доступно и владелец поручает полный контроль, выполняется `FULL_LOCAL`; обнаруженные ошибки исправляются обычным циклом.

Для Codex при локальной работе недоступность MCP требует допустимого fallback: если доступен Ren'Py SDK/CLI — выполнить эквивалентный lint и запуск напрямую. Нельзя писать «MCP checks passed», если MCP фактически не использовался.

## 10. Что писать в отчете

Для любой технической реализации, затрагивающей Ren'Py, указывать:

- уровень проверки: `FULL_LOCAL` или `REMOTE_LIMITED`;
- Git/diff/dependency checks: что именно выполнено;
- MCP diagnostics: какие проверки выполнены и итог, либо явно `не выполнялись`;
- Ren'Py lint: фактический результат либо `не выполнялся`;
- preview/runtime: фактический результат либо `не выполнялся`;
- вручную проверенные экранные потоки, если применимо;
- известные внешние проблемы отдельно от ошибок текущей работы.

Не перечислять инструменты как выполненные, если они не запускались.

## 11. Definition of Done и уровень уверенности

### Для `FULL_LOCAL`

Ren'Py-реализация считается полностью локально проверенной, когда:

- Git diff соответствует требованиям;
- применимые MCP-диагностики/эквивалентные проверки не показывают новых ошибок от текущей работы;
- Ren'Py lint выполнен без новых ошибок;
- для runtime/UI изменений выполнен preview/launch и проверен его статус;
- отчет содержит реальные результаты проверок;
- оставшиеся внешние проблемы явно отделены от результатов текущей работы.

### Для `REMOTE_LIMITED`

Реализация может быть завершена и зафиксирована в GitHub после доступных удаленных проверок, но **не называется полностью runtime-проверенной**. В отчете обязательно сохраняется отметка о непроведенном локальном lint/preview.

Если формальный TASK передается в `review` после `REMOTE_LIMITED`, это явно указывается в implementation report. Перевод в `done` остается решением владельца по общим правилам проекта.

## 12. Внешний инструмент

Используемый MCP-проект: `fracturedring/renpy-mcp`.

Его собственная документация описывает набор MCP diagnostics, `get_lint_report`, `launch_preview`, `get_preview_status` и guarded write pipeline. Настоящий документ определяет **проектную политику Nastya Story** поверх этих возможностей и имеет приоритет внутри данного репозитория.

## 13. RPBuilder GUI

`RPBuilder` — браузерный GUI, поставляемый вместе с `fracturedring/renpy-mcp`. Для Nastya Story он считается **необязательным ручным инструментом инспекции**, а не частью обязательного проверочного контура.

Его можно использовать владельцу или разработчику для обзорного просмотра Story Map, списка characters, variables и screens, а также для ручного запуска доступных операций. При этом:

- RPBuilder не является источником канона;
- его Story Map не считается полным графом sandbox-архитектуры Nastya Story;
- список Assets может быть неполным, поскольку upstream scanner индексирует прежде всего явные Ren'Py `image`/`layeredimage` declarations и audio play references, а не обязан отображать каждый файл графики, лежащий в каталогах проекта;
- список Screens может использоваться как индекс существующих `screen` declarations, но GUI не обязан давать визуальное редактирование уже существующего сложного кастомного screen;
- наличие или отсутствие сущности в RPBuilder не заменяет проверку фактического `.rpy`-кода и MCP diagnostics;
- устанавливать или запускать RPBuilder для каждой задачи не требуется.

При `FULL_LOCAL` обязательным остается применимый контроль из разделов 2–11. При `REMOTE_LIMITED` действует раздел 9.

## 14. Локальная совместимость и диагностика установки

Локальная установка `fracturedring/renpy-mcp` является внешним tooling и не фиксирует зависимость игрового проекта Nastya Story от конкретного Python environment. Однако при проблемах запуска сначала следует отличать неисправность MCP-сервера от ошибки проекта.

Проверочная команда для существующего проекта может запускаться напрямую через Python-модуль, например:

`python -m renpy_mcp --project <PROJECT_ROOT> --sdk <RENPY_SDK> -v`

Если сервер успешно запускается и остается ждать stdio-клиента, базовый MCP-процесс исправен.

На проверенной Windows-установке upstream `renpy-mcp` с его текущим широким требованием `mcp>=1.2.0` мог установить несовместимую major-версию пакета `mcp`, что проявлялось ошибкой вида `AttributeError: 'Server' object has no attribute 'list_tools'`. Рабочим локальным решением для такой конкретной ошибки было ограничение MCP SDK веткой 1.x (`mcp>=1.27,<2`). Это **troubleshooting note**, а не зависимость игры: применять pin только если установленная upstream-комбинация действительно воспроизводит эту ошибку или пока upstream сам не зафиксирует совместимый диапазон.

Если Windows application-control блокирует сгенерированный console shim `rpbuilder.exe`, тот же launcher можно запускать как Python-модуль: `python -m renpy_mcp_gui.launcher`. Это не требуется для автоматических проверок и относится только к ручному запуску RPBuilder.
